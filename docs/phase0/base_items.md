# Phase 0 research: base item classes & ModItems registry pattern (area: base_items)

Scope: `com.hbm.items` base/abstract classes and marker interfaces (not the ~440 concrete item
subclasses in `com.hbm.items.<subpackage>`, which is Phase 1 content).

## Class inventory

| CE file | Purpose |
|---|---|
| `ItemBase.java` | Root superclass for almost every hbm item. Constructor sets translation key, registry name, default creative tab (`MainRegistry.controlTab`), and self-registers into `ModItems.ALL_ITEMS`. |
| `EffectItem.java` | Marker subclass of `ItemBase` for items that only exist as dummy stacks for status-effect rendering; never obtainable, excluded from JEI/creative. No added behavior. |
| `BrokenItem.java` | Concrete-ish item (`ModItems.broken_item`) representing a "broken" wrapper around another item/meta pair, stored via `itemID`/`itemMeta` NBT keys. Overrides display name to show "Broken <wrapped item>". Client-side baked-model machinery composites the wrapped item's model with an overlay (`BrokenItemModel`, `BrokenItemOverrideList`, `CompositeModel` - all 1.12 `IBakedModel`/`ItemOverrideList` classes, obsolete under NeoForge's model system). |
| `ItemBakedBase.java` | `ItemBase` + `IDynamicModels` + `IClaimedModelLocation`. Base for single-texture items that need a manually baked/retextured model (`item/generated` retexture pattern) rather than a static per-item JSON model. Registers itself into `IDynamicModels.INSTANCES` and `ClaimedModelLocationRegistry`. |
| `ItemEnumMulti.java` | Generic `ItemBase` subclass driving 1.12 "one item, N metadata variants" pattern (`hasSubtypes`, per-meta texture/name derivation from an `Enum`). Implements `IDynamicModels`/`IClaimedModelLocation` to bake/retexture one model per enum constant. Also carries one hardcoded gameplay hook (`item_expensive` tooltip line) that leaked into the base class. |
| `ItemEnumMultiFood.java` | Same "one item, N enum variants" pattern as `ItemEnumMulti` but extending vanilla `ItemFood` instead of `ItemBase`/`Item` (duplicated because 1.12 Java has no multiple inheritance). Variant enum must implement the nested `FoodSpec` interface (`foodLevel()`, `saturation()`, `wolfFood()`, `alwaysEdible()`). |
| `ItemAmmoEnums.java` | Holds ammo-variant enums (`AmmoFireExt`, `AmmoMisc`, `Ammo240Shell`) implementing `IAmmoItemEnum` (`getTraits()`, `getInternalName()`), used by the weapon/ammo item classes (out of scope, `com.hbm.items.weapon`). |
| `ItemEnums.java` | Grab-bag of plain, dependency-free enums (`EnumCokeType`, `EnumTarType`, `EnumBriquetteType`, `SoyuzSkinType`, `EnumLegendaryType`, `EnumAshType`, `EnumPlantType`, `EnumChunkType`, `EnumAchievementType`, `EnumFuelAdditive`, `EnumPages`, `EnumSecretType`, `EnumCasingType`, `EnumIngotMetal`, `EnumCircuitType`, `EnumDepletedRTGMaterial`, `EnumPartType`, `ScrapType`, `CircuitComponentType`, `EnumExpensiveType`, `EnumDrillType`). Every enum exposes a static `VALUES` cache. No item logic, pure data. |
| `ItemInventory.java` | `ItemStackHandler` subclass giving an `ItemStack` (crate, containment box, toolbox) its own sub-inventory. Persists slot contents into the owning stack's NBT (`"items"` NBTTagList, see `ItemStackUtil.addStacksToNBT`/`readStacksFromNBT` outside scope) on every content change, and has an NBT-size safety valve (`checkNBT`, gzip-compresses and, if the container tag exceeds 6000 bytes, ejects the contents into the world instead of persisting them). Also plays open/close sounds. |
| `ClaimedModelLocationRegistry.java` | Client-only registry mapping `ModelResourceLocation` -> `IModelLocationOwner`/`ITeisrBinding`, used so 1.12's global item-model bake/override pipeline can find which item instance owns a given baked-model location (including a "synthetic TEISR binding" concept for items whose real render is a TileEntityItemStackRenderer stand-in). Entirely a 1.12 `ModelBakeEvent`/`IBakedModel` era construct. |
| `IAnimatedItem.java` | Interface: `getAnimation(NBTTagCompound, ItemStack)` returning a `BusAnimation` (client rendering, `com.hbm.render.anim`, out of scope) - marks items with a custom held-item animation. |
| `IClaimedModelLocation.java` | Interface extending `IModelLocationOwner`; adds a static helper `isInventoryLocation` comparing a `ModelResourceLocation` against an item's expected `<item>#inventory` location. Pure 1.12 baked-model plumbing. |
| `ICustomizable.java` | Interface: `customize(EntityPlayer, ItemStack, String... args)` - a generic "run a customization command on this item" hook (used by things like creative-only debug items). |
| `IDynamicModels.java` | Interface + static registry (`INSTANCES`, a `ReferenceOpenHashSet`) driving 1.12's era of manual per-item model baking, sprite stitching, custom `StateMapper`, and item/block color-handler registration, all wired through Forge client events (`ModelBakeEvent`, `ColorHandlerEvent`, `TextureMap`). Fully obsolete design under NeoForge (`ItemModelProvider`/data-gen model JSONs + `RegisterColorHandlersEvent` replace all of it). |
| `IDynamicSprites.java` | Smaller, older sibling of `IDynamicModels` for items whose only need is a sprite registered into the atlas at runtime (`TextureMap`). Same NeoForge-obsolescence note applies. |
| `IEquipReceiver.java` | Interface with two default no-op methods, `onEquip(EntityPlayer, EnumHand)` / `onEquip(EntityPlayer, ItemStack)`, called by armor/equip-slot-change handling logic (out of scope, likely in `com.hbm.handler`). |
| `IItemControlReceiver.java` | Interface: `receiveControl(ItemStack, NBTTagCompound)` - generic "server received a client-sent control packet for this held item" hook (used by items with custom keybind/GUI interactions). |
| `IKeybindReceiver.java` | Interface: `canHandleKeybind`/`handleKeybind`/`handleKeybindClient(..., HbmKeybinds.EnumKeybind, boolean)` - items that react to hbm's custom keybinds (`com.hbm.handler.HbmKeybinds`, out of scope). |
| `IModelLocationOwner.java` | Interface: `ownsModelLocation(ModelResourceLocation)` plus a default `loadModel` building an `ItemLayerModel` from the location. Base of the `IClaimedModelLocation` model-ownership chain. |
| `IModelRegister.java` | Trivial interface: `void registerModels()`. |
| `ISatChip.java` | Interface for "satellite frequency chip" items: default `getFreq`/`setFreq` reading/writing an int `"freq"` NBT key on the stack, plus static `getFreqS`/`setFreqS` convenience wrappers that type-check `stack.getItem() instanceof ISatChip`. |
| `ModItems.java` | The ~2855-line, ~440-entry static item registry. **Skimmed for pattern only.** Every field is `public static final Item <name> = new <ItemSubclass>("<registry_name>", ...).set...()`; construction itself performs registration via the base-class side effects (`ModItems.ALL_ITEMS.add(this)` in `ItemBase`'s constructor, plus each subtype's own `INSTANCES`/`ClaimedModelLocationRegistry` registration). There is no explicit `GameRegistry.register` call in this class - CE relies on a separate registration pass (elsewhere, out of scope) iterating `ModItems.ALL_ITEMS`. |

## Key responsibilities of this area

1. Provide the common `Item` superclass (`ItemBase`) that every concrete item in Phase 1 will extend, carrying registry-name/translation-key/creative-tab wiring.
2. Provide the two "one item, many metadata variants" base classes (`ItemEnumMulti`, `ItemEnumMultiFood`) that a large fraction of the ~440 items build on.
3. Provide marker/behavior interfaces (`IEquipReceiver`, `IKeybindReceiver`, `IItemControlReceiver`, `ICustomizable`, `ISatChip`, `IAnimatedItem`) that Phase 1 item classes mix in for cross-cutting behavior hooks invoked by handler code outside this scope.
4. Provide the entirely-1.12-specific dynamic model/sprite/baked-model machinery (`IDynamicModels`, `IDynamicSprites`, `IModelLocationOwner`, `IClaimedModelLocation`, `ClaimedModelLocationRegistry`, `ItemBakedBase`, and `BrokenItem`'s baked-model inner classes) that let a single item render N different textures/models chosen at runtime from metadata/NBT, without per-variant Item subclasses or per-variant blockstate/model JSON at build time.
5. Provide `ItemInventory`, the NBT-backed per-stack sub-inventory used by container items.
6. Provide the `ModItems` registration pattern that Phase 1 agents populate with the real item catalog.

## Cross-area dependencies

- `ItemBase` depends on `com.hbm.main.MainRegistry.controlTab` (creative tab) - owned by another area/phase; in the port this becomes a `CreativeModeTab` `DeferredHolder<CreativeModeTab, CreativeModeTab>` reference, not something this area defines.
- `ItemEnumMulti` references `ModItems.item_expensive` directly inside `addInformation` - this is a leaked cross-reference from base class into a single concrete item; the port should not carry this into the generic base class (see Risks).
- `ItemAmmoEnums` references `com.hbm.items.weapon.ItemAmmo.AmmoItemTrait` (Phase 1 weapon package, out of scope) - the enums in this file are unusable without that class, but the file only *declares* the ammo variant enums+their trait/name accessors, so it can port as-is with the `ItemAmmo` reference left as a forward reference to Phase 1.
- `ItemInventory` depends on `com.hbm.util.ItemStackUtil` (`readStacksFromNBT`/`addStacksToNBT`, out of scope) and `com.hbm.lib.HBMSoundHandler` (open/close sounds, out of scope).
- `IKeybindReceiver` depends on `com.hbm.handler.HbmKeybinds.EnumKeybind` (out of scope).
- `BrokenItem`'s client baked-model inner classes depend on `com.hbm.Tags` (MODID) only, but their *approach* (`IBakedModel`, `ModelBakeEvent`, `ItemOverrideList`) has no 1:1 NeoForge 21.1 equivalent (see port plan).
- `ModItems.java` (skimmed) pulls in essentially every other item subpackage (`items.armor`, `items.bomb`, `items.food`, `items.gear`, `items.machine`, `items.special`, `items.tool`, `items.weapon`, ...) - confirms it is purely a Phase 1 concern once the registry skeleton exists.

## Recommended NeoForge / Java 21 port plan

Target package: `com.hbm.items` in our port project.

1. **`ModItems.java`** - port as an *empty* skeleton only:
   ```java
   package com.hbm.items;

   import com.hbm.main.HbmMod; // or whatever the real MODID constant holder is named in our port
   import net.minecraft.world.item.Item;
   import net.neoforged.bus.api.IEventBus;
   import net.neoforged.neoforge.registries.DeferredItem;
   import net.neoforged.neoforge.registries.DeferredRegister;

   public class ModItems {
       public static final DeferredRegister.Items ITEMS = DeferredRegister.createItems(HbmMod.MODID);

       public static void register(IEventBus modEventBus) {
           ITEMS.register(modEventBus);
       }
   }
   ```
   Confirmed real against Neo Edition's `NtmItems.java` (`DeferredRegister.Items DeferredRegister.createItems(String)`, `DeferredItem<Item> ITEMS.register(String, Supplier<Item>)`). Phase 1 agents add `DeferredItem<Item>` fields the same way `NtmItems` does (including small per-family helper methods like their `registerNugget(String)` for repetitive patterns). Per the task rules, `register(IEventBus)` is documented here for the integration step to call from `MainRegistry`, not wired in by this agent.
   - Registry ids: CE's string registry names (e.g. `"broken_item"`) map straight to `ResourceLocation.fromNamespaceAndPath(MODID, name)` under `DeferredRegister.createItems`, i.e. ids are preserved unchanged.

2. **`ItemBase.java`** - port to a small `Item` subclass. CE's mutable "set stuff after construction" style (`setTranslationKey`, `setRegistryName`, `setCreativeTab`) has no equivalent in 1.21: translation key is derived automatically from registry name, registry name is supplied via `DeferredRegister.register(name, ...)` rather than set on the item, and creative tab membership is a `CreativeModeTab` registration concern, not an `Item` field. So `ItemBase` in the port becomes essentially:
   ```java
   public class ItemBase extends Item {
       public ItemBase(Properties properties) {
           super(properties);
       }
   }
   ```
   with the `ModItems.ALL_ITEMS.add(this)` bookkeeping dropped (DeferredRegister already gives Phase-1/integration code a full iterable list via `ITEMS.getEntries()`), and creative-tab placement moved to wherever `BuildCreativeModeTabContentsEvent` is handled (out of this area's scope - flagged as an open question below since CE's `setCreativeTab` calls are scattered across every `ModItems` entry).

3. **`EffectItem.java`** - trivial 1:1 port as `class EffectItem extends ItemBase`, same doc comment about being excluded from creative/JEI (EMI/REI equivalent membership is decided at Properties/tab level in the port, not in the class).

4. **`ItemEnumMulti.java` / `ItemEnumMultiFood.java`** - these do not port 1:1. Their entire purpose (N metadata values -> N textures/names on one `Item`) is obsolete: 1.21 items no longer have `hasSubtypes`/damage-as-metadata, and "N variants of one conceptual item" is idiomatically N separate registered `Item`s (as Neo Edition's own port already does - e.g. their `NUGGET_*` entries are all distinct `DeferredItem<Item>`s rather than one multi-meta item). Recommendation: **do not port these two classes as base classes for Phase 1 to extend**. Instead:
   - Port the *data* half only: an enum's per-variant name/property/food-spec information stays useful and should be preserved as-is (e.g. `ItemEnums`'s enums, and `FoodSpec`-shaped data), but the eventual "one Item per enum constant" registration happens in `ModItems`/Phase 1, not through a shared multi-meta superclass.
   - This is flagged as a **risk/open question** below rather than silently decided, since it changes how Phase 1 populates ~40-80 previously-multi-meta items into N distinct registry entries; the actual per-family split (which items keep a shared `Item` class with a stored variant, vs. which become fully separate registrations) is a Phase 1 design decision, not something to bake into this area's base classes.
   - `ItemEnumMultiFood`'s `FoodSpec` interface (`foodLevel()`, `saturation()`, `wolfFood()`, `alwaysEdible()`) maps directly onto vanilla 1.21's `FoodProperties` builder (`.nutrition(int)`, `.saturationModifier(float)`, wolf-favorite via the `is_wolf_food`... - actually 1.21 has no "wolf favorite" concept comparable to 1.12; that hook simply does not port and should be dropped or reimplemented as a tag-based check elsewhere) and `Item.Properties.food(FoodProperties)`. This is a Phase 1 concern per-item.

5. **`ItemAmmoEnums.java`, `ItemEnums.java`** - both are pure data (enums, no engine API calls beyond `com.google.common.collect.ImmutableSet` in `ItemAmmoEnums`, which is still on the classpath under NeoForge via Guava). Port verbatim, package-for-package, only removing the now-unnecessary `import com.hbm.items.weapon.ItemAmmo` forward reference note (kept as a compile dependency Phase 1 will satisfy) and swapping nothing else - these are 1:1 already.

6. **`ItemInventory.java`** - `ItemStackHandler` (`net.neoforged.neoforge.items.ItemStackHandler`) is still a real, current NeoForge 21.1 class (confirmed by convention; it is NeoForge's own capability-backing default impl, unchanged in spirit from 1.12's Forge equivalent) so the class shape survives. What must change:
   - **NBT tag compound reads/writes on `ItemStack` must become Data Components.** CE stores the sub-inventory as a `"items"` `NBTTagList` directly in the stack's tag compound (via `ItemStackUtil.addStacksToNBT`/`readStacksFromNBT`, out of scope but load-bearing for this class). Vanilla 1.21 already ships exactly this shape as `DataComponents.CONTAINER` / `ItemContainerContents` (`net.minecraft.world.item.component.ItemContainerContents`), which is a `List<ItemStack>`-backed component with a built-in codec and stream codec, used by vanilla's own shulker boxes and bundles. Recommendation: back `ItemInventory` by reading/writing `ItemContainerContents` on the target stack via `DataComponents.CONTAINER` instead of inventing a custom `DataComponentType`.
     - **NBT key -> Data Component mapping:** `"items"` (NBTTagList of per-slot compounds with a `"slot"` byte + serialized stack) -> `DataComponents.CONTAINER` (`ItemContainerContents`, vanilla-provided, `DataComponentType<ItemContainerContents>`).
   - The 6000-byte gzip-compressed NBT-size safety valve (`checkNBT`/`compress`) is a 1.12-era concern (raw NBT size on the wire); Data Components are still serialized to NBT for saving and have their own size considerations, but the specific gzip-and-measure approach in `checkNBT` is very much tied to `NBTTagCompound`/`CompressedStreamTools` APIs that no longer exist in this form. This method's fate (drop it, since `ItemContainerContents` naturally caps at the container's declared slot count and vanilla bundles/shulkers do not carry this kind of overflow-eject logic; or reimplement a slot-count/stack-size limit check instead of a byte-size check) is flagged as an **open question for whoever ports the concrete container items in Phase 1**, since it is gameplay-behavior-affecting and this agent's mandate is base classes/interfaces, not gameplay decisions.
   - `player`/`target` fields, `openInventory`/`closeInventory` sound hooks, and the constructor's "player + target stack + slot count" shape all survive unchanged in spirit; only the persistence layer (steps above) and the sound-handler reference (`HBMSoundHandler`, out of scope, presumably already ported or being ported by another area) change.

7. **`BrokenItem.java`** - the item-identity concept (wrap another item+meta, show "Broken X") survives, but:
   - `itemID`/`itemMeta` NBT keys -> replaced by real Data Components. **NBT key -> Data Component mapping:** `"itemID"` (string, an `Item` registry name) + `"itemMeta"` (int, 1.12 damage/meta value) together represented one wrapped `ItemStack` identity; in 1.21 metadata/damage-as-identity does not exist, so this collapses to a single custom `DataComponentType<ItemStack>` (e.g. `hbm:wrapped_item`, built with `DataComponentType.<ItemStack>builder().persistent(ItemStack.CODEC).networkSynchronized(ItemStack.STREAM_CODEC).build()`, following the exact `DataComponentType.builder()` shape Neo Edition already uses in `NtmDataComponents.java` for their own custom component) storing the wrapped `ItemStack` directly, rather than two separate primitive keys.
   - The entire baked-model overlay/composite-model machinery (`BrokenItemModel`, `BrokenItemOverrideList`, `CompositeModel`, `ModelBakeEvent`, `IBakedModel`, `ItemOverrideList`) is 1.12/Forge-era client rendering with no direct NeoForge 21.1 equivalent; 1.21's item rendering pipeline uses `ItemModel`/`ItemModel.Unbaked` + a `select`/`composite` item-model-definition JSON structure (or a custom `ItemModel` registered via `RegisterGeometryLoaders`... to be confirmed by whichever area owns client rendering) instead of runtime `ModelBakeEvent` composition. Porting this rendering logic correctly requires the client-rendering conventions the item-rendering-area agent (or a later phase) will establish, so this agent scopes `BrokenItem` to: (a) the item class, its constructor(s), its `make(...)` static factory helpers rewritten to build/read the new `hbm:wrapped_item` component, and (b) its display-name override reading that component - **without** attempting to port the baked-model inner classes, which are flagged as an explicit **out-of-scope / needs-client-rendering-area-decision** item.

8. **`ItemBakedBase.java`, `ItemAmmoEnums.IAmmoItemEnum`... (already covered), `IDynamicModels.java`, `IDynamicSprites.java`, `IModelLocationOwner.java`, `IClaimedModelLocation.java`, `ClaimedModelLocationRegistry.java`** - all of this is the 1.12 runtime model-baking/sprite-stitching/model-location-ownership machinery for "one item renders as N different things chosen from metadata/NBT at runtime, without per-variant models baked at build time." None of it has a direct NeoForge 21.1 analogue: 1.21's item rendering is data-driven via item model definition JSON (`assets/<mod>/items/<name>.json`) with `minecraft:select`/`minecraft:composite`/`minecraft:condition` item model types that key off Data Components (including custom ones), generated normally via `ItemModelProvider`-style datagen rather than a runtime Java event listener. Recommendation: **do not port these classes into the base-item package.** They are pure 1.12 rendering plumbing whose entire reason to exist (dynamic runtime model baking) is replaced wholesale by 1.21's component-driven item model JSON system. This is called out explicitly as an area this agent is **not implementing** (per the "no half-finished implementations" rule, and because item-model-JSON authoring is squarely a client-rendering-area concern, not base item classes) - it is not Phase 1 content either; it is dropped as a design in favor of the vanilla 1.21 mechanism.

9. **Remaining marker interfaces** (`IAnimatedItem`, `ICustomizable`, `IEquipReceiver`, `IItemControlReceiver`, `IKeybindReceiver`, `ISatChip`, `IModelRegister`) - port 1:1 as plain Java interfaces with updated Minecraft/NeoForge types (`net.minecraft.world.item.ItemStack`, `net.minecraft.world.entity.player.Player`, `net.minecraft.world.InteractionHand`, `net.minecraft.core.component...` where NBT is involved). Specifically:
   - `ISatChip`'s `getFreq`/`setFreq` currently read/write an int `"freq"` NBT key -> **NBT key -> Data Component mapping:** `"freq"` (int) -> a new custom `DataComponentType<Integer>` (e.g. `hbm:sat_freq`), built exactly like Neo Edition's own `NtmDataComponents.META` example (`DataComponentType.<Integer>builder().persistent(Codec.INT).networkSynchronized(ByteBufCodecs.INT).build()`). The default-method shape (`getFreq(ItemStack)`/`setFreq(ItemStack, int)`) survives, only the storage call changes from `stack.getTagCompound().getInteger("freq")` to `stack.getOrDefault(HbmDataComponents.SAT_FREQ, 0)` / `stack.set(HbmDataComponents.SAT_FREQ, freq)`. Note: the actual `HbmDataComponents` registry class does not exist in scope yet (Neo Edition's equivalent, `NtmDataComponents`, lives in `com.hbm.items.component` - out of this agent's file list) - flagged as an **open question**: which area/phase owns creating our port's `com.hbm.items.component.HbmDataComponents` (or similar) registry class that this interface's default methods would reference.
   - `IAnimatedItem`'s `getAnimation` returns `com.hbm.render.anim.BusAnimation` (out of scope, client rendering) - the interface itself ports unchanged, its return type is a forward reference.
   - `IKeybindReceiver` references `com.hbm.handler.HbmKeybinds.EnumKeybind` (out of scope) - ports unchanged as a forward reference.

10. **`ClaimedModelLocationRegistry.java`** - as covered in point 8, this is being dropped/replaced by 1.21's data-driven item model system rather than ported.

## Risks / open questions

- **Multi-meta item split (biggest open item).** `ItemEnumMulti`/`ItemEnumMultiFood` are used across an unknown but likely large fraction of the ~440 Phase 1 items (metals with multiple grades, coke types, tar types, etc. per `ItemEnums.java`'s enum list). This agent recommends *not* porting a shared multi-variant base class and instead letting each Phase 1 family register N distinct `DeferredItem<Item>`s (matching how Neo Edition's own `NtmItems.java` already handles the equivalent CE multi-meta items, e.g. their uranium/plutonium ingot family). This is a real design decision with real Phase 1 workload impact and should be confirmed/ratified before Phase 1 starts, not silently assumed.
- **Creative tab wiring.** Every single `ModItems` entry in CE ends with `.setCreativeTab(MainRegistry.xTab)`. In 1.21/NeoForge, creative tab membership is set either via `Item.Properties.arch...` no such method exists on Properties for that; it is instead handled through a `BuildCreativeModeTabContentsEvent` listener (or via `CreativeModeTab.Builder.displayItems`) registered separately, not on the `Item`/`ItemBase` constructor itself. This agent's `ItemBase` therefore intentionally does **not** carry a creative-tab parameter or field, unlike CE's. Whoever owns creative tabs (likely a dedicated area) needs to register every item into the right tab; this is called out so Phase 1 agents don't try to bolt a `setCreativeTab`-shaped API onto `ItemBase`.
- **`HbmDataComponents` registry class does not exist yet in our port's scope list.** Two of this area's classes (`ISatChip`, and `BrokenItem`'s wrapped-item storage) need a custom `DataComponentType`, which conventionally lives in its own registry class (Neo Edition's precedent: `com.hbm.items.component.NtmDataComponents`). Creating our port's equivalent is out of this agent's explicit file scope (not listed), so it is documented here rather than silently added; the next stage/integration step should confirm who owns `com.hbm.items.component.HbmDataComponents` (or wherever it should live) and wire this area's two component needs (`hbm:sat_freq` : Integer, `hbm:wrapped_item` : ItemStack) into it.
- **`BrokenItem` rendering.** As noted in the port plan, this agent scopes `BrokenItem` to the item class + data-component-backed identity/display-name logic only; the composite-overlay rendering is explicitly left unimplemented pending the client-rendering area's item-model-JSON conventions, per the "no half-finished implementations for whatever you DO implement" rule - the rendering piece is simply not implemented in Phase 0 by this area, not stubbed.
- **`ItemEnumMulti`'s leaked `ModItems.item_expensive` reference.** CE's base class contains one hardcoded per-item tooltip check (`if(this == ModItems.item_expensive) ...`). Since (per the point above) this agent does not recommend porting `ItemEnumMulti` as a shared base class at all, this leak is moot for the port - flagged here only so nobody looks for a "faithful" 1:1 translation of `ItemEnumMulti` and wonders where this line went.
- **`ItemInventory`'s 6000-byte NBT-size eject-to-world safety valve.** Flagged in the port plan above as a gameplay-behavior decision for whoever ports the concrete container items (crates/containment boxes/toolbox, all out of this area's scope) in Phase 1, since Data-Component-backed containers don't have an obvious 1:1 replacement for "container tag got too big, dump contents on the ground."
- **`ItemStackHandler` availability confirmed by convention, not by direct citation in the Neo Edition reference** - grepping the reference tree did not turn up a live NeoForge 21.1 usage of `net.neoforged.neoforge.items.ItemStackHandler` in the files this agent inspected. It is an extremely well-established, unchanged-in-shape NeoForge capability helper class (same package/class name across Forge and NeoForge since long before 1.21), so this agent treats it as a "well-established convention" per the task's guidance rather than an invented API, but the integration step should double check this compiles against the exact 21.1.228 NeoForge jar.

# Phase 0 research report - Base block classes & ModBlocks registry pattern

Area key: `base_blocks`
Scope: `com.hbm.blocks` base/abstract classes and marker interfaces (excluding the ~620 files under `com.hbm.blocks.<subpackage>`, which are Phase 1/2 content).

## 1. Class inventory

| CE file | Purpose |
|---|---|
| `BlockBase.java` | Generic concrete `Block` base class used directly (not abstract) for hundreds of simple decorative/structural blocks. Sets translation key, registry name, harvest level (pickaxe/0), creative tab, self-registers into `ModBlocks.ALL_BLOCKS`. Carries a mutable `noSpawn` flag (fluent `setNoSpawn()`) that suppresses mob spawn placement, and an `addInformation` override that adds a blast-resistance tooltip line and a "no spawn" tooltip line, plus one special-cased Tesla-coil hint keyed off `ModBlocks.meteor_battery`. |
| `BlockContainerBakeableNormal.java` | Abstract `BlockContainer` base for TE-backed blocks that bake a custom model at runtime from a `BlockBakeFrame` (retextured `cube_all` model) instead of a static blockstate JSON. Implements `IDynamicModels`. Purely a 1.12 baked-model/`ModelBakeEvent` mechanism - the whole approach is obsolete under 1.21's data-driven model system. |
| `BlockControlPanelType.java` | Tiny `IStringSerializable` enum (`CUSTOM_PANEL`, `FRONT_PANEL`) used as a blockstate property value set for control-panel-style blocks. |
| `BlockDummyable.java` | The most important class in this scope. Abstract `BlockContainer` base for every multiblock structure's non-core "dummy" placeholder blocks. Encodes structure orientation and rotation into a single `PropertyInteger META` (0-15: 0-5 dummy-to-core direction, 6-11 same + "extra" flag for pipe-connector-like dummies, 12-15 core block rotation for TE rendering). Responsibilities: walking the dummy chain to find the structure's core (`findCore`/`findCoreTE`, iterative with a hard step cap of 512 to avoid infinite loops), placing the whole structure and validating space on placement (`onBlockPlacedBy`, `checkRequirement`, `fillSpace`, delegating to `MultiblockHandlerXR`), an iterative (not recursive, deliberately, to avoid stack overflow on long dummy chains) orphan-cascade removal when a neighboring dummy or the core is destroyed (`cascadeOrphans`/`isOrphan`, guarded by a static `safeRem` flag so the batch of `setBlockToAir` calls doesn't re-enter `neighborChanged`), detailed per-block collision-box support for irregularly shaped multiblocks (`bounding`, `addCollisionBoxToList`, `getAABBRotationOffset"), client-side ghost/placement-preview rendering (`drawPlacementHighlight`, raw GL11 immediate-mode line drawing), and forwarding "info panel" queries (`ICopiable.getSettings/pasteSettings`, `infoForDisplay`) from any dummy position to the real TE at the core. Implements `ICustomBlockHighlight`, `ICopiable`, `INBTBlockTransformable` (structure-file rotation remap), `IDynamicModels`. |
| `BlockDummyableMBB.java` | Abstract subclass of `BlockDummyable` for multiblocks whose footprint is declared as a set of arbitrary `AxisAlignedBB` boxes (via `MultiblockBBHandler.REGISTRY`) rather than a fixed rectangular `int[] getDimensions()`. Overrides `checkRequirement`/`fillSpace` to rasterize the rotated boxes into a per-block-position map of sub-boxes, validate placement against `canPlaceBlockAt` and eye-position clearance (`Library.checkForPlayerEyePositions`), then stamp each covered block with a directional dummy meta pointing back at the core. |
| `BlockEnumMeta.java` | Generic `<E extends Enum<E>>` subclass of `com.hbm.blocks.generic.BlockMeta` (out of scope, but the direct superclass) that drives an entire metadata-block family off a Java enum: generates one `BlockBakeFrame.cubeAll(...)` per enum constant, and supplies an inner `ItemBlock` (`EnumMetaBlockItem`) whose translation key is derived per-metadata from the enum name when `multiName` is set. |
| `BlockEnums.java` | Pure data: a bag of unrelated `enum` types consumed by many different metadata-block families elsewhere (stone types, meteor types, cabinet/CRT/toaster deco variants, ore overlay types with an `IOreType`-adjacent enum, basalt ore drops wired directly to `ModItems` fields, platemetal color variants, etc). No behavior beyond a couple of `getDrop()`/`getDropCount()` helpers that reference `ModItems`. |
| `BlockFallingBase.java` | Concrete `BlockFalling` subclass (sand/gravel-like blocks) with the same self-registration boilerplate as `BlockBase`, plus two hardcoded joke/lore tooltip blocks (`gravel_diamond`, `sand_boron`) identified by direct `==` comparison against `ModBlocks` fields. |
| `IAnalyzable.java` | One-method interface (`getDebugInfo(World, BlockPos)`) for blocks that can report debug info to some analyzer tool. Comment in CE notes it is not yet implemented by fluid-network blocks. |
| `IBlockMulti.java` | Interface for "meta block" families: `getSubCount()`, plus default `getTranslationKey(ItemStack)` / `getOverrideDisplayName(ItemStack)` / `rectify(int)` (modulo-clamp a metadata value into the valid enum range). |
| `ICustomBlockHighlight.java` | Interface + two `static` helper methods for opting a block out of vanilla block-outline rendering and drawing a custom one instead (`shouldDrawHighlight`/`drawHighlight`, `setup()`/`cleanup()` wrapping raw `GlStateManager` blend/line-width state). Entirely 1.12 fixed-function-pipeline rendering. |
| `ICustomBlockItem.java` | Default-method interface that, instead of the vanilla `ItemBlock`, registers a hasSubtypes/no-repair `ItemBlock` (inner class `CustomBlockItem`) for blocks with metadata-driven item variants. |
| `ILookOverlay.java` | Interface for blocks that draw a custom HUD overlay when looked at (`printHook`), plus a `static printGeneric` helper that does raw `FontRenderer`/`GlStateManager` HUD text drawing with an inline `&[0xRRGGBB]` color-escape mini-format. |
| `IOreType.java` | Interface pairing a `BiFunction<IBlockState, Random, ItemStack>` drop function with a `TriFunction<IBlockState, Integer, Random, Integer>` fortune-aware quantity function. Implemented by the `OreEnum` enum in `OreEnumUtil`. |
| `IPersistentInfoProvider.java` | Interface for adding tooltip lines derived from an item's persistent-info NBT tag (`addInformation(ItemStack, NBTTagCompound, EntityPlayer, List<String>, boolean)`). |
| `ISpotlight.java` | One-method interface (`getBeamLength()`) for blocks that project a light beam (searchlights etc). |
| `IStepTickReceiver.java` | Interface for blocks that want a callback when a player walks over them (`onPlayerStep`), presumably driven by a central step-tracking handler elsewhere (out of scope). |
| `ITooltipProvider.java` | Default-method interface providing the mod's standard "hold shift for more info" tooltip convention plus a default `EnumRarity`. Carries an explicit, detailed doc comment warning against invoking `addInformation` through this interface type due to SRG remapping/AbstractMethodError risk in the 1.12 dev/obfuscated split - this concern is 1.12/MCP-mapping-specific and does not apply once the whole codebase is Mojang-mapped in 1.21. |
| `MaterialGas.java` | `net.minecraft.block.material.Material` subclass for non-solid, non-grass-blocking, non-movement-blocking "gas" pseudo-blocks (used for radiation/gas-cloud effect blocks). `Material` as a settable per-block "physical category" object does not exist in modern Minecraft; block physical behavior is expressed instead as `BlockBehaviour.Properties` flags and voxel shapes. |
| `ModSoundType.java` | `net.minecraft.block.SoundType` subclass supporting per-block custom place/break/step `SoundEvent`s, several static factory permutations (`customPlace`, `customBreak`, `customStep`, `customDig`, `placeBreakStep`, copy-from-existing variants), and a nested `ModEnvelopedSoundType` that applies a randomized volume/pitch "envelope" function per sub-sound-type (place/break/step) - used for things like pipe placement sounds with slight pitch variance. `SoundType` in 1.21 has the same open constructor shape (volume, pitch, break/step/place/hit/fall `Holder<SoundEvent>`), so this ports mechanically modulo the `SoundEvent` vs `Holder<SoundEvent>` wrapping. |
| `ModSoundTypes.java` | Two concrete `ModSoundType` instances (`grate`, `pipe`) built from the above factories and `HBMSoundHandler` sound fields (out of scope registry). |
| `OreEnumUtil.java` | Static drop-quantity helper functions (`base2Rand3Fortune` etc, all `(IBlockState, int fortune, Random) -> int`) and drop-item helper functions, plus the large `OreEnum implements IOreType` enum enumerating every vanilla ore block's drop (coal/diamond/emerald) and every modded ore's drop, each wired to a `ModItems` field via either a direct `ItemStack` supplier or a `BiFunction`. This is squarely ore *content* (30+ ore families) even though the *utility functions and interface plumbing* belong to this area. |
| `PlantEnums.java` | Pure data: three enums (`EnumDeadPlantType`, `EnumFlowerPlantType`, `EnumTallPlantType`) describing plant block variant sets, with a `needsOil` flag per flower/tall-plant variant used by crop-growth logic elsewhere. |
| `ModBlocks.java` (skimmed only, 1617 lines) | Confirms the registration pattern used by every class above: a single `public static List<Block> ALL_BLOCKS` collected by base-class constructors as a side effect (**not** a Forge/NeoForge registry API at all - this is CE's own bespoke bootstrap list, later iterated to bulk-register into `ForgeRegistries.BLOCKS`), one `public static final Block someName = new SomeBlockClass(...).setHardness(...).setResistance(...)` field per block, and a couple of `Material` singletons (`materialGas`). This pattern is being replaced wholesale in the port by `DeferredRegister.Blocks` per the NeoForge 1.21 convention - `ModBlocks.ALL_BLOCKS`-style self-registration must NOT be carried into the port. |

## 2. Key responsibilities of this area

1. **Common block boilerplate** (`BlockBase`, `BlockFallingBase`, `BlockContainerBakeableNormal`): translation key / registry name / creative tab / harvest level wiring that every simple block in the mod currently repeats through inheritance.
2. **The multiblock dummy-block contract** (`BlockDummyable`, `BlockDummyableMBB`): the single most load-bearing piece of this area. Every multiblock machine (reactors, turbines, factories, etc, all Phase 2 content) places a core block plus a shell of "dummy" blocks that redirect all interaction back to the core's tile entity. This class owns: the encoding scheme for direction+rotation in block metadata, core-finding, placement validation and space-filling, and safe (non-recursive) mass removal when the structure is broken.
3. **Metadata-block family plumbing** (`BlockEnumMeta`, `IBlockMulti`, `ICustomBlockItem`): the generic machinery for "one block, many textures/names driven by an enum via metadata," which in 1.21 is replaced by real distinct `Block` registry entries per variant (metadata blocks are gone from vanilla Minecraft since 1.13).
4. **Cross-cutting marker interfaces** (`IAnalyzable`, `ICustomBlockHighlight`, `ILookOverlay`, `IOreType`, `IPersistentInfoProvider`, `ISpotlight`, `IStepTickReceiver`, `ITooltipProvider`): small optional-capability contracts that individual block subclasses (Phase 1/2 content, out of scope here) opt into.
5. **Shared enum catalogs** (`BlockEnums`, `PlantEnums`, `OreEnumUtil`'s `OreEnum`): variant lists consumed by many out-of-scope block subclasses. These are largely inert data and port almost verbatim as plain Java enums, modulo the direct `ModItems` field references.
6. **Custom `Material`/`SoundType` subclasses** (`MaterialGas`, `ModSoundType`, `ModSoundTypes`): physical-property and audio customization hooks with no 1:1 modern equivalent for `Material` (see risks below).

## 4. Recommended NeoForge 1.21.1 / Java 21 port plan

Verified against the Neo Edition reference (`com.hbm.blocks.NtmBlocks`, `com.hbm.blocks.generic.NoSpawnBlock`, and the various `appendHoverText` overrides across `com.hbm.blocks.*`), which is a real, building NeoForge 21.1 codebase.

### 4.1 `ModBlocks` registry (the deliverable requested for this area)

Create `com.hbm.blocks.ModBlocks` as an **empty** scaffold, following the confirmed Neo Edition shape:

```java
public class ModBlocks {
    public static final DeferredRegister.Blocks BLOCKS = DeferredRegister.createBlocks(HbmMod.MODID);

    // Later phases add DeferredBlock<...> fields here, using the private register()
    // helpers below (which also register the matching BlockItem into ModItems.ITEMS).

    public static void register(IEventBus modEventBus) {
        BLOCKS.register(modEventBus);
    }
}
```

Do not port `ALL_BLOCKS` or any self-registering-constructor pattern - `DeferredRegister.Blocks` (confirmed real: `net.neoforged.neoforge.registries.DeferredRegister`, `DeferredBlock`) is the registry of record. Later phases populate it exactly the way `NtmBlocks` does: a `private static <T extends Block> DeferredBlock<T> register(String name, Supplier<T> block)` helper that both registers the block and registers a matching `BlockItem` on the items side. Because that helper's `BlockItem` half necessarily touches `ModItems`, this area should define the `register` helper signature/contract in the report (as above) but leave the actual helper body for whichever area first needs to add an entry, since a `BLOCKS`-only class with zero entries has nothing to wire a helper against yet - **or**, if the integration step prefers, this area can pre-declare the no-op `register` helper too, since its shape is already fully confirmed from `NtmBlocks`. I recommend including the helper method (parameterized, unused until Phase 1/2 adds entries) so later phases don't have to touch this file's structure, only add fields.

Registration entry point: expose `ModBlocks.register(IEventBus modEventBus)` (mirroring `NtmBlocks.register(IEventBus)`) for `MainRegistry` to call from its constructor - do not edit `MainRegistry.java` yourself.

### 4.2 `BlockBase`

Port as a thin `Block` subclass taking a `BlockBehaviour.Properties` (built by the caller, matching modern convention - hardness/resistance/sound now live on `Properties`, not mutable setters called after construction). Drop the self-registering constructor entirely (no `ModBlocks.ALL_BLOCKS.add(this)` - registration happens via `DeferredRegister` at the call site instead). Keep:
- The `noSpawn` behavior, ported per the **confirmed** `NoSpawnBlock` pattern: `properties.isValidSpawn(ModBlocks::noSpawn)` (a static `(BlockState, BlockGetter, BlockPos, EntityType<?>) -> boolean` predicate) passed in at construction, since `BlockBehaviour.Properties` is immutable and fixed at construction time in 1.21 - there is no post-construction `setNoSpawn()` fluent setter anymore. Either accept a `boolean noSpawn` constructor flag that conditionally applies the predicate, or require the caller to pass `.isValidSpawn(...)` themselves and keep a `protected final boolean noSpawn` field purely for the tooltip line.
- `appendHoverText(ItemStack, Item.TooltipContext, List<Component>, TooltipFlag)` (confirmed signature from multiple Neo Edition blocks) reproducing the blast-resistance and no-spawn tooltip lines. Use `getExplosionResistance()` (still present on `Block`/`BlockBehaviour`) for the blast-resistance check.
- Drop the special-cased `ModBlocks.meteor_battery`/Tesla-coil tooltip hint from the generic base class - that is single-block content logic that belongs on whatever specific block class represents `meteor_battery` in the port, not in the shared base.

### 4.3 `BlockFallingBase`

Port as a thin `FallingBlock` subclass (still present in 1.21, `net.minecraft.world.level.block.FallingBlock`) with the same `Properties`-based constructor simplification. Drop the two hardcoded joke-tooltip blocks (`gravel_diamond`, `sand_boron` identity checks) from the shared base class for the same reason as 4.2 - move them to the concrete block classes in whichever Phase owns those two blocks, using `appendHoverText` there instead of an `instanceof`/`==` check in the shared base.

### 4.4 `BlockDummyable` / `BlockDummyableMBB` - port faithfully, adapting only what the platform forces

This is the highest-risk, highest-value part of this area since Phase 2's multiblock framework depends on it. Recommended approach:
- Keep it a `BaseEntityBlock` (1.21's renamed `BlockContainer`) implementing `EntityBlock`.
- Replace `PropertyInteger META` (0-15) with an `IntegerProperty META = IntegerProperty.create("meta", 0, 15)` (`net.minecraft.world.level.block.state.properties.IntegerProperty`), registered via `createBlockStateDefinition(StateDefinition.Builder<Block, BlockState>)` instead of `createBlockState()`/`BlockStateContainer`. Keep the exact same 0-15 semantic ranges (dummy direction 0-5, "extra" flag +6, core rotation +10) unchanged - this is pure data encoding, not API-shaped, so it survives the port unchanged and Phase 2 code that assumes these ranges keeps working.
- Replace `ForgeDirection` with vanilla `Direction` (`net.minecraft.core.Direction`) throughout - `ForgeDirection` was CE's own pre-1.8 direction enum kept for legacy code; 1.21 has no reason to keep it and `Direction` already has `getOpposite()`, `getStepX/Y/Z()`, `values()` equivalents. This is a mechanical rename, not a redesign, but touches nearly every method in the class - flag as a deliberate, faithful *substitution* rather than a silent behavior change.
- `neighborChanged`/`updateTick`(now `tick` on `Block` in 1.21, `BlockBehaviour#tick(BlockState, ServerLevel, BlockPos, RandomSource)` - confirm exact signature against the Neo Edition reference when Phase 2 implements it) keep their iterative, non-recursive orphan-cascade logic and the `safeRem` re-entry guard as-is - this is a real, deliberate stack-overflow avoidance, not incidental complexity, and must not be "simplified" back into recursion.
- `onBlockPlacedBy` needs updating for 1.21's `Level`/`Player`/`ItemStack` types and `InteractionHand`, but the placement-orientation math (`MathHelper.floor` -> `Mth.floor`) and the `checkRequirement`/`fillSpace` delegation shape are unchanged.
- `addCollisionBoxToList` becomes `getCollisionShape`/`entityInside`-family API in modern Minecraft (voxel shapes, not raw `AxisAlignedBB` lists) - flag this as a genuine API-shape change requiring `VoxelShape`/`Shapes.create(AxisAlignedBB)` wrapping per rotation state, not a rename.
- Drop `bakeModel`/`registerModel`/`registerSprite`/`getStateMapper`/`drawPlacementHighlight` (raw `GL11/GlStateManager` immediate-mode rendering and 1.12 `ModelBakeEvent` baking) entirely - none of this API exists in 1.21. The equivalent client-side ghost-block-preview rendering (if kept) would need a full rewrite against modern `RenderType`/`PoseStack`/`VertexConsumer` in a client-only renderer class, which is Phase 2/rendering-area territory, not this area. This area should port the **contract** (`getDimensions()`, `getOffset()`, `getHeightOffset()`, `getAllDimensions()`, `getAABBExtras()`) as abstract/overridable methods so Phase 2's multiblocks and a future rendering pass can both depend on them, but should not attempt to port the GL11 drawing code.
- `ICopiable`, `INBTBlockTransformable`, `IDynamicModels` implementations depend on interfaces outside this area's scope - port `BlockDummyable`'s calls to them as-is (calling through the same interface names) and let whichever area owns those interfaces provide their 1.21 shape; if that area has not yet ported them, this becomes a documented open dependency (see Risks).
- `BlockDummyableMBB` ports mechanically once `BlockDummyable`'s `Direction`/`VoxelShape` changes are in place - its box-rasterization math (`clampToPos`, `volume`, `rotate`) is pure arithmetic with no Forge/NeoForge API surface, and `MultiblockBBHandler`/`Library.checkForPlayerEyePositions` are out-of-scope calls to keep as-is.

### 4.5 `BlockContainerBakeableNormal`

**Do not port as a live rendering mechanism.** Its entire purpose (baking a model at runtime from `BlockBakeFrame` via `ModelBakeEvent`) is a 1.12-only mechanism with no 1.21 equivalent - 1.21 blocks get their appearance from JSON blockstate/model files (optionally generated by a `BlockStateProvider` at datagen time) or, for TE-driven custom rendering, a `BlockEntityRenderer`. Recommend: port only the non-rendering plumbing this class's subclasses need (the `Properties`-based constructor, `IDynamicModels`-style client rendering flag if that interface survives elsewhere), and note in this report that its actual purpose is superseded by datagen-time blockstate/model JSON generation, which belongs to Phase 2/asset-pipeline work, not this class.

### 4.6 `BlockEnumMeta`, `BlockControlPanelType`, `IBlockMulti`, `ICustomBlockItem`

**Do not port the metadata-multiplexing mechanism.** Minecraft has had no block metadata since 1.13; every "one block, N metadata variants" family in CE must become N distinct registry entries (N distinct `Block`/`BlockItem` pairs) in the port, typically generated via a loop over the same enum at `ModBlocks` registration time (`for (E variant : E.values()) register(name + "_" + variant.name(), () -> new SomeBlock(variant, props))`), not a single block with a metadata property. Recommend:
- Port `BlockControlPanelType` as a plain enum (it's just data, no metadata coupling itself, though its *use site* elsewhere likely assumed metadata storage - out of scope to fix that use site here).
- Do not port `BlockEnumMeta`, `IBlockMulti`, or `ICustomBlockItem` in their current form. Document the enum-driven multi-variant *pattern* (loop over enum, register N blocks/items, translation key per variant) as the replacement convention for later phases to follow when they hit a CE `BlockEnumMeta` usage, rather than porting a class whose entire premise (shared `BlockMeta` + `PropertyInteger` metadata) no longer applies.

### 4.7 Marker interfaces without a 1.12-only rendering payload

Port essentially as-is, updating parameter types to modern equivalents and confirming exact modern method names against the Neo Edition reference at the point each is first implemented by a concrete block (since none of `IAnalyzable`, `IOreType`, `IPersistentInfoProvider`, `ISpotlight`, `IStepTickReceiver` are implemented by anything in this file list, there's nothing here to cross-check them against yet):
- `IAnalyzable` - `getDebugInfo(Level, BlockPos)`, unchanged shape.
- `IOreType` - `BiFunction<BlockState, RandomSource, ItemStack>` / a `TriFunction<BlockState, Integer, RandomSource, Integer>` (keep CE's own `com.hbm.lib.TriFunction` if it survives the port, otherwise it's a 3-line functional interface to reintroduce in whichever area owns `com.hbm.lib`).
- `IPersistentInfoProvider` - `addInformation(ItemStack, CompoundTag, Player, List<Component>, boolean)`. Note: if the "persistent info" tag in question is stored via a data component on the item rather than raw NBT in the port (per the hard rule on Data Components), this interface's first parameter set should be revisited by whichever area first implements it - flagged as an open question, not resolved here since no concrete NBT key list is visible from this file alone.
- `ISpotlight`, `IStepTickReceiver` - unchanged shape (`int getBeamLength()`; `onPlayerStep(Level, BlockPos, Player)` using a real `BlockPos` instead of raw `int x, int y, int z`, since 1.21 has no reason to keep CE's still-1.7-era raw-coordinate style here).
- `ITooltipProvider` - the "hold shift" default method and default `Rarity` (renamed from `EnumRarity`) port unchanged; drop the entire ABI/remapping warning doc comment, since it describes an MCP/SRG dev-vs-obfuscated mapping split that does not exist once the project is Mojang-mapped end to end.

### 4.8 Two interfaces that are pure 1.12 rendering and should NOT be ported as designed

- `ICustomBlockHighlight` - raw `GlStateManager`/`GL11` immediate-mode block-outline override. 1.21's equivalent hook is a `RenderHighlightEvent.Block` NeoForge event with modern `PoseStack`/`MultiBufferSource` rendering. Port the *contract* (does this block want a custom highlight, given it, draw one) as an interface once a client-rendering area defines the modern event-driven replacement; do not port `setup()`/`cleanup()`.
- `ILookOverlay` - raw `FontRenderer`/`GlStateManager` HUD overlay with a bespoke inline color-escape text format. 1.21 equivalent is a `RenderGuiEvent`/`GuiGraphics`-based hook. Same recommendation: port the contract, not the drawing code, and let a rendering-focused area own the modern implementation.

### 4.9 `MaterialGas`, `ModSoundType`, `ModSoundTypes`

- `ModSoundType`/`ModSoundTypes` port close to mechanically: `net.minecraft.world.level.block.SoundType` still takes `(float volume, float pitch, Holder<SoundEvent> breakSound, Holder<SoundEvent> stepSound, Holder<SoundEvent> placeSound, Holder<SoundEvent> hitSound, Holder<SoundEvent> fallSound)` in modern Minecraft (six sound slots now, vs three in 1.12: break/step/place plus hit/fall are new required slots) - CE's three-sound constructor needs to supply sensible hit/fall defaults (commonly the break/step sound reused) rather than a straight 1:1 argument copy. Recommend confirming the exact `SoundType` constructor arg order/`Holder` wrapping against the Neo Edition reference before implementing (not yet done in this research pass - flagged as an open item for the implementation stage). The `ModEnvelopedSoundType` envelope/pitch-randomization mechanism has no platform dependency and ports unchanged.
- `MaterialGas` **does not port** - `net.minecraft.world.level.material.Material` as a settable "physical category" object was removed years before 1.21; block physicality (pushable/replaceable/solid/blocks-movement) is now expressed per-block through `BlockBehaviour.Properties` flags (`.noCollission()`, `.replaceable()`, `.pushReaction(PushReaction.DESTROY)`, etc) and `MapColor` is passed separately via `.mapColor(...)`. Recommend: wherever CE constructs a block `new SomeBlock(materialGas, ...)`, the port instead builds an appropriate `BlockBehaviour.Properties` chain directly (`Properties.of().mapColor(MapColor.NONE).noCollission().replaceable().pushReaction(PushReaction.IGNORE)` or similar) at each call site - there is no single reusable "MaterialGas" object to carry forward.

### 4.10 `BlockEnums`, `PlantEnums`, `OreEnumUtil`

- `BlockEnums`, `PlantEnums` port as plain Java enums essentially verbatim - no Forge/NeoForge API surface at all. The couple of `getDrop()` methods referencing `ModItems` fields will need updating once `ModItems` exists in the port (out of scope here), but the enum *shape* itself is final now.
- `OreEnumUtil`'s static quantity/drop helper functions and the `IOreType` interface pairing port mechanically (`IBlockState` -> `BlockState`, `Random` -> `RandomSource`). The `OreEnum` enum itself (30+ ore drop definitions referencing `ModItems`/`Items`/`ItemPool`) is genuinely ore **content**, not base-block plumbing - recommend Phase 1's ore-block area owns porting `OreEnum`'s actual entries once `ModItems` exists, while this area only delivers the `IOreType` interface and the reusable quantity-function static methods as the ready-to-use scaffold.

## 5. Data Components note

No `ItemStack` NBT read/write exists anywhere in this area's file list. `IPersistentInfoProvider` takes an already-extracted `NBTTagCompound persistentTag` as a parameter (i.e. some other, out-of-scope code is responsible for pulling that tag off the stack) rather than reading `ItemStack` NBT itself, so there is no NBT-key -> Data-Component mapping to propose from this area. Flagging for whichever area implements `IPersistentInfoProvider`'s call sites: that is where the actual `ItemStack.getTagCompound()`-style access (if any) lives, and where the Data Components hard rule will actually bite.

## 6. Risks and open questions

1. **`Direction` vs `ForgeDirection` migration inside `BlockDummyable`.** This is a mechanical but pervasive substitution (dozens of call sites: `.offsetX/Y/Z`, `.getOpposite()`, `.getOrientation(int)`, `.getRotation(ForgeDirection.UP)`, `.toEnumFacing()`). Recommend doing this substitution carefully method-by-method rather than a blind find/replace, since `ForgeDirection.getOrientation(int)` ordinal mapping must be preserved exactly to keep the `META` 0-15 encoding's semantics intact.
2. **Collision box API change.** `addCollisionBoxToList(IBlockState, World, BlockPos, AxisAlignedBB, List<AxisAlignedBB>, Entity, boolean)` has no direct 1.21 analog - modern Minecraft collision is `VoxelShape`-based (`getCollisionShape`/`getShape`). Faithfully preserving `BlockDummyable`'s per-rotation detailed hitbox behavior requires building a `VoxelShape` (via `Shapes.create(AxisAlignedBB)` unioned per bounding box) per rotation state, ideally cached, rather than a straight method-signature port. This is real design work for whichever phase first implements a detailed-hitbox multiblock, not a mechanical rename - flagging now so Phase 2 doesn't assume it's a drop-in.
3. **`SoundType`'s sound-slot count changed** (3 -> 6, `SoundEvent` -> `Holder<SoundEvent>`) between 1.12 and 1.21. Not yet confirmed against the Neo Edition reference in this research pass (no `ModSoundType`-equivalent class was found there to check against) - the implementation stage should grep the Neo Edition reference's actual vanilla `SoundType` construction call sites (e.g. any custom block overriding `getSoundType`) to confirm exact constructor argument order and `Holder` wrapping before writing `ModSoundType`.
4. **`BlockDummyable`'s dependency on `MultiblockHandlerXR`/`MultiblockBBHandler`** (space-checking/filling backends) is not in this area's scope and, per a quick file-name check, does not appear to exist yet anywhere under this port's `com.hbm.handler` package. Phase 2's multiblock-framework area needs to either already own porting these, or this becomes a hard blocking dependency before `BlockDummyable`/`BlockDummyableMBB` can compile in the port (the classes can still be written and reviewed against CE now, per this area's task, but will not compile stand-alone until that handler exists).
5. **`ICopiable`, `INBTBlockTransformable`, `IDynamicModels`, `IPersistentNBT`** interfaces that `BlockDummyable` implements/calls are likewise not in this area's file list and their 1.21 shape is unknown from here - same blocking-dependency caveat as above.
6. **Whether to pre-declare the `register(...)` helper overloads in the empty `ModBlocks`** (section 4.1). I lean toward including at least the simplest `register(String, Supplier<T>)` overload now since its shape is fully confirmed and it costs nothing while empty, but flagging this as a judgment call for the implementation stage in case the integration step wants `ModBlocks` truly inert (zero methods, only the `DeferredRegister.Blocks` field and `register(IEventBus)`) until a content phase adds the first real entry.
7. **CE's joke/lore tooltip blocks** (`gravel_diamond`, `sand_boron` in `BlockFallingBase`; the meteor_battery/Tesla-coil hint in `BlockBase`) reference specific `ModBlocks` fields that don't exist yet in the port. Recommend explicitly not porting these two special cases into the shared base classes (see 4.2/4.3) and instead noting them here so whichever phase ports `gravel_diamond`/`sand_boron`/`meteor_battery` themselves knows to add the equivalent `appendHoverText` override on those specific block classes, preserving the original joke text faithfully (it is real shipped content/copy, not a stub).

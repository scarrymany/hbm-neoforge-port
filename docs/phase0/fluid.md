# Phase 0 Research: Fluid Type Registry

Area key: `fluid`
Scope read: `com.hbm.inventory.fluid.**`, `com.hbm.api.fluid.**`, `com.hbm.api.fluidmk2.**` (CE, 1.12.2)
Reference read: `com.hbm.fluids.NtmFluidTypes` / `com.hbm.fluids.NtmFluids` (Neo Edition, 1.21.1 NeoForge, confirmed-working API shapes only)

## 1. Class inventory

### `com.hbm.inventory.fluid` (core, in scope for this phase)

| File | Purpose |
|---|---|
| `FluidType.java` | The actual "fluid" definition used everywhere in CE: a plain Java object (NOT a Forge/NeoForge `Fluid`) carrying id, internal name, color, tint, texture `ResourceLocation`, translation key, temperature, poison/flammability/reactivity stats, an `EnumSymbol`, a map of "containers" (rendering metadata objects like `CD_Canister`/`CD_Gastank`), and a map of `FluidTrait` instances keyed by trait class. Has several constructor overloads for: normal fluids (auto-incrementing id via `Fluids.registerSelf`), forced-id fluids (safeguard against ID drift), custom/JSON-defined fluids (`setupCustom`), and "foreign"/compat fluids bridged from other mods (`setupForeign`). Exposes `getFF()` to fetch the matching Forge `Fluid` (1.12 `net.minecraftforge.fluids.Fluid`) if one was registered via compat, and lifecycle hooks (`onTankBroken`, `onTankUpdate`, `onFluidRelease`) that machine tile entities call into. Also owns client-side tooltip building (`addInfo`/`addInfoItemTanks`), which loops all registered `FluidTrait` classes. |
| `Fluids.java` (1212 lines) | The static registry / catalog. Declares ~180 `public static FluidType` fields (100+ genuinely distinct substances, others are hot/cold or leaded/unleaded variants of the same base). `init()` constructs every stock `FluidType` with its full stat/trait/container definition, then a second block populates `metaOrder` (the display/sort order, independent of the immutable registration order). Also owns: id/name lookup maps (`idMapping`, `nameMapping`), NBT read/write helpers (`writeType`/`readType`, name-based with legacy numeric-id fallback), a `renameMapping` for backwards-compat renames, JSON-driven custom fluid definitions (`hbmFluidTypes.json`) and trait-override config (`hbmFluidTraits.json`) read/written via Gson, a `fluidMigration` map so config reloads reuse existing `FluidType` instances instead of creating new ones (machines hold direct references), and Forge-Fluid compat registration (`setupForgeFluidCompat` -> constructs a `net.minecraftforge.fluids.Fluid` subclass `FluidNTM` per `FluidType`, with density/viscosity/gaseous flags derived from traits, and registers a bucket). Static shared trait instances (`LIQUID`, `VISCOUS`, `GASEOUS`, `PLASMA`, `ANTI`, etc.) and pre-built `FT_Polluting` presets (`P_OIL`, `P_FUEL`, `P_GAS`, ...) live here too, reused across dozens of fluid definitions. |
| `FluidStack.java` | Trivial value holder: `(FluidType type, int fill, int pressure)`. Pure data, no MC/Forge dependency at all. Distinct from and unrelated to `net.minecraftforge.fluids.FluidStack` (the vanilla-Fluid-based one), which is only used at the `IFluidHandler` capability boundary inside `FluidTankNTM`. |

### `com.hbm.inventory.fluid.trait` (in scope)

| File | Purpose |
|---|---|
| `FluidTrait.java` | Abstract base for all traits. Static registry (`traitList`, `traitNameMap`: a `HashBiMap<String, Class<? extends FluidTrait>>`) mapping a JSON-config trait name (e.g. `"corrosive"`) to its class, used by the `hbmFluidTraits.json` reader/writer in `Fluids`. Defines the extension points: `addInfo`/`addInfoHidden` (tooltip text), `onFluidRelease` (world-release behavior, e.g. spill/burn/void), and `serializeJSON`/`deserializeJSON` (per-trait config persistence). Nested `FluidReleaseType` enum (`VOID`, `BURN`, `SPILL`). |
| `FluidTraitSimple.java` | Container class holding all the zero-config "tag" traits as static nested classes: `FT_Gaseous`, `FT_Gaseous_ART`, `FT_Liquid`, `FT_Viscous`, `FT_Plasma`, `FT_Amat`, `FT_LeadContainer`, `FT_Delicious`, `FT_Unsiphonable`, `FT_NoID`, `FT_NoContainer`. Most only override `addInfoHidden` to print a bracketed tag when the player holds shift. |
| `FT_Corrosive.java` | Configurable trait: `rating` (0-100, drives `isHighlyCorrosive()` at >50) plus tooltip and JSON (de)serialization. |
| `FT_Combustible.java` | `FuelGrade` enum (`LOW`/`MEDIUM`/`HIGH`/`AERO`/`GAS`) plus `combustionEnergy` (long), used by engines/generators to pick a burn rate/output. |
| `FT_Coolable.java` | Reactor coolant trait; carries a `CoolingType` enum and cooling-value fields (not fully read line-by-line but structurally mirrors `FT_Heatable`/`FT_Combustible`). |
| `FT_Corrosive.java`, `FT_Flammable.java`, `FT_Heatable.java`, `FT_Pheromone.java`, `FT_Poison.java`, `FT_Polluting.java`, `FT_PWRModerator.java`, `FT_Rocket.java`, `FT_Toxin.java`, `FT_VentRadiation.java` | Each a self-contained, JSON-(de)serializable configurable trait with its own numeric parameters (e.g. `FT_Flammable(long)`, `FT_VentRadiation(float)`, `FT_Rocket(int, long)` for rocket-fuel thrust/isp-like stats, `FT_Polluting` which accumulates `PollutionType -> rate` pairs via a fluent `.burn(...)`/`.release(...)` builder consumed by `PollutionHandler`, `FT_Toxin` with nested `ToxinDirectDamage`/`ToxinEffects` enums tied to `HbmPotion`/`MobEffects`). All follow the same shape as `FT_Corrosive`/`FT_Combustible` above. |

### `com.hbm.inventory.fluid.tank` (referenced, mostly out of scope for this phase)

| File | Purpose |
|---|---|
| `FluidTankNTM.java` | The machine-side tank implementation. Implements Forge's `IFluidHandler`/`IFluidTank` capability interfaces (1.12 `net.minecraftforge.fluids.*`), holds a `FluidType` + fill/max/pressure, does GUI rendering (raw `Tessellator`/`GlStateManager` calls), NBT persistence via `Fluids.writeType`/`readType`, netty `ByteBuf` (de)serialization for network sync, and item-loading logic delegated to `IFluidLoadingHandler` implementations. This is the "machine tank" the task description explicitly defers to a later phase. |
| `FluidLoaderStandard/Forge/Infinite/FluidLoaderFillableItem.java`, `IFluidLoadingHandler.java` | Strategy objects for filling/draining `FluidTankNTM` from held items (canisters, Forge-fluid containers, infinite source items, `IFillableItem` items). Depend on `IItemHandler` slots and `ModItems` - squarely inventory/GUI territory, later phase. |

### `com.hbm.api.fluid` (deprecated shim, in scope but trivial)

All 5 interfaces (`IFluidConnector`, `IFluidConnectorBlock`, `IFluidStandardReceiver/Sender/Transceiver`) are `@Deprecated` one-line shims that just `extends` the corresponding `fluidmk2` interface, kept only for old third-party code compiled against the pre-MK2 API. No independent logic.

### `com.hbm.api.fluidmk2` (referenced, out of scope - belongs to the pipe/network phase)

`FluidNetMK2` extends the generic `NodeNet<...>` (shared with `energymk2`'s power network) and implements the actual multi-provider/multi-receiver, pressure-tiered, priority-based fluid transfer simulation between machines (`FluidNode`, `IFluidProviderMK2`, `IFluidReceiverMK2`, `IFluidConnectorMK2`, `IFluidPipeMK2`, `IFillableItem`, `IFluidRegisterListener`, `IFluidUserMK2`). This is the pipe/network layer, analogous to the power grid - it is a large, separate subsystem that only depends on `FluidType` (one field) and otherwise has nothing to do with "fluid type registration." Confirmed out of scope per task description ("not machine tanks" implies not the network layer feeding them either); flagged here only so a later phase knows `FluidType.getNetworkProvider()` (in `FluidType.java`) is the seam where `FluidNetMK2` plugs in.

## 2. Key responsibilities of this phase's actual scope

1. A registry of ~100+ named, mutable `FluidType` "substance" definitions (id, display data, physical stats, traits) - this is CE's own domain model, not a NeoForge registry object at all in 1.12.
2. A trait system (`FluidTrait` + subclasses) that attaches optional, independently JSON-configurable behavior/metadata to a `FluidType` (corrosive rating, flammability, combustion grade/energy, pollution profile, radiation venting, etc.), consumed by tooltips and by machine logic elsewhere in the mod.
3. Id/name lookup + NBT round-tripping for tile-entity-held fluid state (`FluidTankNTM` and friends, out of scope, but they call into `Fluids.writeType/readType`).
4. Optional bridging of a `FluidType` to a real placeable/bucket-able Forge `Fluid` (`setupForgeFluidCompat`) - used sparingly (mostly for compat, e.g. JAOPCA integration), NOT for every fluid.
5. JSON-driven customization: server-owner-added custom fluids (`hbmFluidTypes.json`) and trait overrides (`hbmFluidTraits.json`), loaded at postinit via `reloadFluids()`.

This is a clean, mostly self-contained data-model area.

## 4. Recommended NeoForge / Java 21 port plan

**Core insight:** CE's `FluidType` is *not* the same concept as NeoForge's `net.neoforged.neoforge.fluids.FluidType`. CE's class is an internal "substance" record used for machine tank contents, tooltips, and gameplay stats; it only optionally gets bridged to a real placeable/bucketable fluid. NeoForge's `FluidType` (confirmed via the Neo Edition reference, `NtmFluidTypes`/`NtmFluids`) is the 1.21 replacement for Forge's old `Fluid`/`FluidRegistry`, used together with `Fluid`/`BaseFlowingFluid` and a `DeferredRegister` when you actually want a placeable, flowable world fluid with a bucket. Per the task's port spec ("most without world blocks"), the overwhelming majority of the ~180 CE fluid entries do NOT need a NeoForge `FluidType`/`Fluid` pair at all in this phase - only the registry of substances does.

Plan:

1. **Keep the package** `com.hbm.inventory.fluid` and **keep the class shapes** `FluidType`, `Fluids`, `FluidStack`, `FluidTrait` (+ `trait` subpackage) essentially 1:1, mechanically updated for MC 1.21.1/Mojang mappings:
   - `net.minecraft.tileentity.TileEntity` -> `net.minecraft.world.level.block.entity.BlockEntity`
   - `net.minecraft.world.World` -> `net.minecraft.world.level.Level`
   - `net.minecraft.util.ResourceLocation` -> `net.minecraft.resources.ResourceLocation` (unchanged simple name, new package)
   - `net.minecraft.util.text.TextFormatting` -> `net.minecraft.ChatFormatting`
   - `net.minecraftforge.fml.relauncher.Side`/`SideOnly` -> drop; gate client-only tooltip code with `FMLEnvironment.dist.isClient()` or simply leave it callable only from client-only call sites (`addInfo` is already only ever invoked from item tooltip code) - no direct NeoForge annotation equivalent needed since NeoForge no longer requires physical-side annotations.
   - `org.lwjgl.input.Keyboard.isKeyDown(...)` -> `org.lwjgl.glfw.GLFW.glfwGetKey(...)` / `Screen.hasShiftDown()` (Neo Edition confirms `Screen` static helpers are the idiomatic 1.21 replacement; verify exact usage against Neo Edition's client tooltip code when this area's client-rendering counterpart is ported - out of scope here, flag for the tooltip/rendering phase).
   - `net.minecraft.nbt.NBTTagCompound` -> `net.minecraft.nbt.CompoundTag` (only used for `FluidTankNTM`'s block-entity save state via `Fluids.writeType/readType` - block-entity NBT is unaffected by the Data Components migration rule, since it is not `ItemStack` NBT).
   - `HashBiMap` (Guava) - available unchanged as a dependency; no change needed.
2. **Drop the `net.minecraftforge.fluids.Fluid getFF()` / `setupForgeFluidCompat` machinery** from this phase's port. There is no 1:1 "generic bucket-able Fluid per substance" concept carried over automatically in modern Forge/NeoForge the way old Forge's `FluidRegistry` allowed; NeoForge fluids are heavier (require `FluidType` + `Fluid`/`BaseFlowingFluid` singletons + a registered `Item` bucket + blockstate/model). Recommend: keep `FluidType.getFF()`-equivalent as a stubbed extension point (`Optional<Holder<net.minecraft.world.level.material.Fluid>> getWorldFluid()`) that a **later** phase (blocks/fluid-networks) fills in per-substance, only for the small number of fluids that actually need to exist as placeable world fluid (e.g. an oil ocean feature, or lava-like fluids as NeoForge's `NtmFluidTypes.VOLCANIC_LAVA_TYPE`/`NtmFluids.VOLCANIC_LAVA` demonstrate). Do not attempt to auto-register 180 NeoForge `FluidType`+`Fluid` pairs; that would be scope creep into blocks/rendering and mostly wasted since CE never gives most of them a world presence either (`setupForgeFluidCompat` was opt-in per fluid via `additionalListeners`/compat code, not automatic for every entry).
3. **Provide one small `DeferredRegister`-based class for the minority of substances that DO need a real NeoForge fluid**, following the confirmed working pattern from `NtmFluidTypes`/`NtmFluids`:
   ```java
   private static final DeferredRegister<FluidType> FLUID_TYPES =
       DeferredRegister.create(NeoForgeRegistries.Keys.FLUID_TYPES, Tags.MODID);
   private static final DeferredRegister<Fluid> FLUIDS =
       DeferredRegister.create(BuiltInRegistries.FLUID, Tags.MODID);
   ```
   Expose `public static void register(IEventBus modEventBus)` (name to be wired by the integration step into `MainRegistry`, per the task's rule against editing `MainRegistry.java` directly) so later phases can add entries to it as they port fluid blocks. In Phase 0 this class can be created essentially empty (no world fluids ported yet), or omitted entirely and created fresh when the first fluid block is actually ported - recommend the latter to avoid dead/unused scaffolding, per the "no half-finished implementations" rule. **Decision needed from whoever owns the blocks/fluid-networks phase**: is it in scope now or later? Flagging as open question below.
4. **Keep `Fluids.init()` as a single large static initializer** populating the same ~180 `public static FluidType` fields with identical stats/colors/traits, preserving registration order (hence numeric id order) exactly as CE has it, since `FluidType`'s forced-id constructor and comment both stress "ALWAYS append new fluid entries AT THE BOTTOM." This is pure data - a big, mechanical, low-risk transcription task for the next (implementation) stage, not something to redesign.
5. **JSON custom-fluid / trait-override config** (`hbmFluidTypes.json`, `hbmFluidTraits.json`) - keep using Gson (already a mod dependency in CE; confirm it's still bundled/available in the 1.21 toolchain via NeoForge's included Gson, which it is) with the same file-based read/write logic, updated only for `MainRegistry.configHbmDir`-equivalent (whatever the ported config directory accessor ends up being called - a `main`-package concern, not this area's).
6. **No `DataComponentType`/ItemStack-NBT migration applies to this area.** Everything this phase's scope touches persists to **block-entity** NBT (`FluidTankNTM.writeToNBT`/`readFromNBT`, using `Fluids.writeType`/`readType`) or to network `ByteBuf`, never to `ItemStack` NBT. `FluidStack` (`com.hbm.inventory.fluid.FluidStack`) is a plain in-memory transfer object, never serialized to an `ItemStack` directly in the scoped files. If a later phase discovers an `ItemStack`-held fluid container (e.g. a filled canister item) storing its `FluidType`/fill NBT directly on the stack, that NBT key (something like `"fluid"`/`"fill"`, defined in the `items.machine`/`inventory.container` area, not in this area's scope) will need a `DataComponentType<FluidStackComponent>` with a codec - explicitly flagged as an open question for whoever ports fluid-holding items, since it is outside this area's file scope.

## 5. Risks / open questions

- **World-fluid scope boundary**: is any fluid block/bucket work wanted in Phase 0, or strictly deferred? The task description implies deferred ("not fluid blocks... those are later phases"); this report treats the `DeferredRegister<FluidType>`/`DeferredRegister<Fluid>` scaffolding as optional/deferred too, since building it with zero real entries would be exactly the kind of placeholder scaffolding the task rules prohibit ("No placeholder assets, no TODO stubs, no half-finished implementations"). Recommend: skip creating the NeoForge fluid `DeferredRegister` class entirely in Phase 0, and let the phase that first needs a real placeable fluid (a lava-like block, etc.) create it then, modeled directly on `NtmFluidTypes`/`NtmFluids`.
- **Client-only code paths** (`addInfo`, `addInfoItemTanks`, `Keyboard.isKeyDown`) need a real, verified 1.21/NeoForge idiom for "is shift held" in tooltip-building code outside a `Screen` context (item tooltips are typically built via `Item.appendHoverText`, which does have access to shift-state through `TooltipFlag.isAdvanced()` is NOT the same as shift-detection - the actual CE mechanic is Keyboard-polling, which needs a client-side utility). This is a rendering/tooltip concern that should be resolved by whichever phase ports the item/tooltip rendering code, not by this area, but the trait `addInfo`/`addInfoHidden` methods that call into it are defined in this area's scope (`FluidTrait`), so the *signature* stays but the *shift-detection call site* is a cross-area dependency to flag.
- **`FT_Rocket`, `FT_PWRModerator`, `FT_Pheromone`, `FT_Toxin`, `FT_Heatable`, `FT_Coolable`, `FT_VentRadiation`, `FT_Flammable`, `FT_Poison`** were confirmed to exist and follow the same self-contained configurable-trait shape as `FT_Corrosive`/`FT_Combustible` (constructor + getters + `addInfo` + JSON (de)serialize) by directory listing and by the two read in full, but were not each individually read line-by-line in this research pass given the volume (23 trait files total); the implementation stage should read each one before porting, since a couple (`FT_Toxin`, `FT_Coolable`) reference other cross-area enums (`HazardClass`, `CoolingType`) whose owning areas should be confirmed ported first or stubbed with real matching enum values (not fabricated ones).
- **`Fluids.java` is 1212 lines** with ~180 fields and two large parallel blocks (`init()`'s construction block, and the separate `metaOrder.add(...)` block) that must stay in sync; a transcription-stage risk is drifting the two lists apart. Recommend the implementation stage diff the two lists against each other bidirectionally after porting (every field constructed in `init()` must appear exactly once in the `metaOrder` block, including `customFluids`/`foreignFluids` appended at the end) rather than trusting a single read-through.
- **`renameMapping`** (declared but its population site was not located within the first ~450 lines read) and **legacy numeric-id NBT fallback** (`Fluids.readType`) exist purely for save-compatibility with old CE worlds; since this is a from-scratch NeoForge port with a new save format boundary anyway, confirm with the project lead whether legacy-save compatibility is even a goal for this port (if not, the numeric-id fallback path and `renameMapping` could be simplified away - flagging rather than deciding, since "preserve behavior" and "don't invent scope-reducing shortcuts" both apply and this is a product decision, not an engineering one).

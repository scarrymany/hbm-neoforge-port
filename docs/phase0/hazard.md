# Phase 0 Research: Hazard System Registry (`com.hbm.hazard`)

Source of truth: `hbm-ce/src/main/java/com/hbm/hazard/**` (28 files).
Reference only (partial existing port, API shapes confirmed real): `neo-edition/src/main/java/com/hbm/hazard/**` (15 files, incomplete: no CONTAMINATING/TOXIC/COLD/UNSTABLE/DangerousDrop types, no async scan pipeline, no transformers besides the base interface, no HazardHelper).

## 1. Class inventory

### Root (`com.hbm.hazard`)

| File | Purpose |
|---|---|
| `HazardData.java` | Mutable builder: a bag of `HazardEntry` plus an `override` flag (purges prior entries gathered for a stack) and a `mutexBits` int (mutually-exclusive registration groups, e.g. ore-dict aliases). Built up via `addEntry(...)` chaining at registration time. |
| `HazardEntry.java` | One `(IHazardType type, double baseLevel, List<IHazardModifier> mods)` triple. `applyHazard` runs the modifier chain then calls `type.onUpdate`. `clone(mult)` scales `baseLevel` (used by fluid-content transformer to scale per mB). |
| `HazardRegistry.java` | The static data-table: ~150 named radioactivity/level constants (per-isotope Rad/s values transcribed from a physics reference table in comments) plus the 11 `IHazardType` singleton instances (`RADIATION`, `CONTAMINATING`, `DIGAMMA`, `HOT`, `BLINDING`, `ASBESTOS`, `COAL`, `HYDROACTIVE`, `EXPLOSIVE`, `TOXIC`, `COLD`). `registerItems()` is the ~460-line bulk registration of hazard data for concrete CE items (fuel rods, RBMK rods/pellets, RTG pellets, PWR fuel, nuclear waste variants, nuke cores, etc.) plus a handful of private helper methods (`registerRBMKRod`, `registerRTGPellet`, `registerOtherFuel`, `registerPWRFuel`, `registerOtherWasteContaminating`, ...) that wire up type-specific `IHazardModifier`s. `registerTrafos()` builds the `IHazardTransformer` chain. `registerContaminatingDrops()` back-fills `CONTAMINATING` entries onto already-registered ore-dict dust entries after `OreDictManager` runs. |
| `HazardSystem.java` | The engine. Three lookup maps (`oreMap: String->HazardData`, `itemMap: Item->HazardData`, `stackMap: ComparableStack->HazardData`) plus `stackBlacklist`/`dictBlacklist` sets and a `trafos` list. `register(...)`/`unregister(...)`/`blacklist(...)` overloads dispatch by argument runtime type (String/Item/Block/ItemStack/ComparableStack/ResourceLocation, plus Collection/array expansion for bulk (un)register). `getHazardsFromStack` resolves ore-dict -> item -> exact-stack in that priority order, honoring `override`/`mutex`, and runs `IHazardTransformer.transformPre/transformPost` around the merge. Results are cached two ways: an NBT-agnostic `hazardDataChronologyCache` (keyed by `ComparableStack`) and an NBT-sensitive `finalHazardEntryCache` (Guava cache, keyed by stack + a *sanitized* NBT hash that deliberately excludes the neutron-contamination NBT key so neutron buildup doesn't defeat the cache); a `volatilityTracker` blacklists a stack's cache key entirely if it's produced too many distinct NBT hashes too quickly (protects against unbounded cache growth from highly dynamic NBT). The public API also exposes `applyHazards`, `getHazardLevelFromStack`, `getRawRadsFromStack`/`getTotalRadsFromStack` (adds `ContaminationUtil` neutron rads), `updateDroppedItem` (called from an ASM hook on `EntityItem`), and `addHazardInfo` (tooltip). Player-facing effect application is a **heavily CE-specific, threaded, event-driven rewrite** (explicit `@author` note says "do not aim for upstream parity"): `onServerTickAsync` is driven from a server tick event, batches per-player inventory deltas (`onInventoryDelta`, fed by a container/slot-change hook) and periodic full rescans onto a background executor via `CompletableFuture`, then applies the resulting per-slot "applicator" `Consumer<EntityPlayer>` closures back on the main thread through `PlayerHazardData.applyActiveHazards()`, which is also where neutron-activation math (`ContaminationUtil`) and `hazardRate`-scaled tick throttling live. |

## 2. Key responsibilities of this area

- Define the **hazard type taxonomy** (11 concrete effect behaviors) as a small, closed, mostly-stateless strategy set (2 types, `HazardTypeDangerousDrop`/`HazardTypeUnstable`, are parametric strategy *factories* rather than fixed singletons).
- Provide a **registry keyed by ore-dict-name / Item / exact ItemStack(meta)** that resolves, for any `ItemStack`, an ordered list of applicable `HazardEntry` (type + level + modifier chain), with override/mutex semantics for conflicting registrations.
- Provide a **transformer pipeline** for hazard sources that cannot be captured by static registration alone: raw NBT tags, fluid contents, nested-stack containers, AE2 virtual storage, and a generic addon-facing extension point.
- Provide a **modifier chain** for hazard sources whose *level* is dynamic based on item state (fuel depletion, RBMK enrichment/xenon poisoning, RBMK hull heat, RTG pellet depletion) without changing the type of hazard.
- Own the **CE-specific runtime engine** that walks player inventories on a schedule/on-change, evaluates hazards, and applies their effects, plus a two-level caching/volatility-protection scheme so this doesn't become a per-tick hot path cost.
- Own the ~460-line **bulk data registration** binding CE's ~150 physics-derived constants to concrete CE items (nuclear waste variants, RBMK/RTG/PWR fuel families, nuke cores, etc.) - this specific call, `HazardRegistry.registerItems()`, is explicitly **out of scope for this research task** per the task's stated Phase 1 boundary (458-item catalog), but the *registry mechanism* it calls into is in scope.

## 4. Recommended NeoForge / Java 21 port plan

The existing (partial) Neo Edition port at `neo-edition/src/main/java/com/hbm/hazard` already validates the core shape and was used to confirm real NeoForge 21.1 APIs; it is missing ~40% of CE's type/transformer surface and all of CE's threaded scan engine, both of which are CE enhancements that should be preserved per the "CE is source of truth" rule.

**Package layout** - keep 1:1: `com.hbm.hazard`, `.helper`, `.modifier`, `.transformer`, `.type`.

**Core registry mechanism (in scope for this task):**
- `IHazardType` -> keep as an **interface** (CE deliberately refactored it from an abstract class to an interface; preserve that intent) with `LivingEntity`/`ItemEntity`/`Player` Mojang-mapped types replacing `EntityLivingBase`/`EntityItem`/`EntityPlayer`. Client-only tooltip method annotated `@OnlyIn(Dist.CLIENT)` (NeoForge's real replacement for `@SideOnly(Side.CLIENT)`, confirmed in the Neo Edition reference). Tooltip signature becomes `List<Component>` instead of `List<String>` (Neo Edition reference confirms this).
- `IHazardModifier`, `IHazardTransformer` -> keep as interfaces (both CE and the "shut the fuck up" comment style already treat interface-vs-abstract-class as an intentional stylistic choice by CE; the Neo Edition reference happens to use abstract classes for these - either is legal NeoForge code, but to respect "preserve CE's own logic/structure", keep CE's interface choice since it costs nothing and matches CE's stated mlbv refactor comments).
- `HazardData`/`HazardEntry` -> near-verbatim port, `double` fields preserved as CE has them (CE upgraded these from Neo Edition's/original `float` to `double` deliberately - keep `double`, it's more precise and is what CE's source of truth uses).
- `HazardSystem` registry maps:
  - **Ore-dict replacement**: 1.12's `OreDictionary` string-keyed system has no direct 1.21 equivalent; the confirmed real replacement (per Neo Edition reference, `HazardSystem.tagMap`) is `HashMap<TagKey<Item>, HazardData>` using `ItemStack.getTags()` / `TagKey<Item>.isFor(Registries.ITEM)`. This is a straightforward, low-risk mechanical substitution for the *lookup* mechanism. Populating the actual tag set that mirrors CE's ore-dict names (`ingotUranium`, `dustCoal`, etc.) is Phase 1 (item/tag catalog) work, not this task's.
  - `itemMap: Item -> HazardData`, `stackMap: ComparableStack -> HazardData`, `stackBlacklist`, `tagBlacklist` (renamed from `dictBlacklist`) - all port mechanically; `ComparableStack` itself lives in `com.hbm.inventory.RecipesCommon` (out of scope, cross-area dependency, confirmed still used unmodified by the Neo Edition reference).
  - `register(Object, HazardData)` dispatch-by-type overloads: keep CE's fuller multi-overload public API (String/Item/Block/ItemStack/ComparableStack/ResourceLocation/Collection/array) rather than the Neo Edition reference's single collapsed `Object` overload, since CE's version is a richer, already-shipped public API that groovy/addon consumers may depend on; adapt the `String oreName` overload to accept `TagKey<Item>` instead (breaking but necessary - ore-dict strings do not exist in 1.21). The `ResourceLocation`-deferred-registration path (`locationRateRegisterList`) becomes unnecessary noise in NeoForge, since DeferredRegister callbacks / `RegisterEvent` already guarantee registry population order - drop that mechanism and register hazard data directly against `DeferredItem<Item>`/`DeferredBlock<Block>` `.get()` results at mod-init time (confirmed pattern in Neo Edition's `HazardRegistry.item(...)`/`block(...)` helpers), or against vanilla `Items.*`/`Blocks.*` directly.
  - `getHazardsFromStack` core merge algorithm (tag -> item -> stack priority, override/mutex handling, pre/post transformer wrapping) - port mechanically, it is registry-shape logic with no Minecraft-version-specific API surface.
  - **Threaded scan/cache engine** (`onServerTickAsync`, `PlayerHazardData`, the two-tier cache, volatility tracking, `InventoryDelta` batching): this is pure CE business logic added on top of the base mechanism, uses only `java.util.concurrent` plus a Guava `Cache` (both fine on Java 21/NeoForge) and one Forge-1.12-specific hook point (`FMLCommonHandler.instance().getMinecraftServerInstance()` inside a `ServerTickEvent` handler and a container-slot-change ASM hook feeding `onInventoryDelta`). Port plan: replace `FMLCommonHandler`/`ServerTickEvent` with NeoForge's `ServerTickEvent.Post` (`net.neoforged.neoforge.event.tick.ServerTickEvent`) fired on the mod event bus/game bus per NeoForge 21.1 convention, and replace the ASM slot-change hook with a `PlayerContainerEvent`/`ContainerEventHandler`-equivalent NeoForge event, or (simpler, lower-risk) have `PlayerHazardData.calculateHazardScanForPlayer` be the only mechanism initially (full periodic rescan, no delta fast-path) and reintroduce the delta optimization in a later phase once the exact NeoForge container-change event is confirmed against a real working example - **flagging this as an open question**, see Risks.
  - The `EntityItem`-ASM-hook entry point (`updateDroppedItem`) has no ASM in NeoForge; replace with a real NeoForge event, e.g. `net.neoforged.neoforge.event.entity.item.ItemTossEvent` does not fit (this needs *periodic per-tick* dropped-item hazard ticking, not toss); the correct replacement is almost certainly a tick handler on `ItemEntity` via `EntityTickEvent.Post` filtered to `ItemEntity`, confirmed as a real NeoForge event type. Needs a name-exact check against a working example before implementation (see Risks) - do not guess the payload/dispatch semantics.
- `HazardHelper` - port mechanically; "reacher" item check and potion-effect helper have no version-specific hazards, only Mojang-mapping renames (`EntityLivingBase`->`LivingEntity`, `Potion`->`Holder<MobEffect>`/`MobEffect`, `PotionEffect`->`MobEffectInstance` - all confirmed real 1.21 Mojang-mapped names via well-established NeoForge convention and consistent with `HazardTypeCold`/`HazardTypeToxic` needing `MobEffects.*` constants, which the Neo Edition reference does not yet exercise for these types but which are stable, well-known vanilla registry constants).
- `modifier` package - port all 4 concrete modifiers mechanically; each is pure math/branching against another item class's static accessor, so correctness is bottlenecked on Phase 1 porting those item classes (`ItemRBMKRod`, `ItemRBMKPellet`, `ItemRTGPellet`) with equivalent accessor methods, not on anything in this package.
- `transformer` package - port all 5 concrete transformers, with two 1.12-Forge-API replacements needed:
  - `HazardTransformerForgeFluid`: Forge 1.12 `IFluidHandlerItem`/`CapabilityFluidHandler.FLUID_HANDLER_ITEM_CAPABILITY`/`IFluidTankProperties` becomes NeoForge 21.1's `IFluidHandlerItem` capability obtained via `stack.getCapability(Capabilities.FluidHandler.ITEM)` (confirmed real capability accessor pattern per NeoForge 21.1 `Capabilities` conventions used elsewhere in the Neo Edition reference tree - verify exact accessor name against a live Neo Edition fluid-capability usage before implementation, not guessed here since none was read in this task's scope).
  - `HazardTransformerRadiationME`: AE2 is an optional soft dependency; `Loader.isModLoaded` becomes NeoForge's `ModList.get().isLoaded(...)`. AE2's own 1.21 API surface is outside this task's knowledge; treat as a Phase-later compat shim, not Phase 0/1 critical path.
  - `HazardTransformerRadiationNBT`, `HazardTransformerRadiationContainer`, `HazardTransformerPostCustom`: see Data Component mapping below - these are the ones that read/write raw NBT and must change.

## 5. Risks / open questions

1. **Neutron-contamination coupling is the biggest structural risk.** `HazardSystem`'s entire NBT-sensitive caching strategy (`getSanitizedNbtHash`) exists specifically to exclude `ContaminationUtil.NTM_NEUTRON_NBT_KEY` from the cache key so that per-tick neutron buildup doesn't invalidate the hazard cache on every tick. If/when `ContaminationUtil` migrates neutron tracking off raw NBT (Data Components or an attachment), this entire sanitization scheme needs a redesign, not a mechanical port - it should be flagged for whoever owns `ContaminationUtil`'s port, and the two teams need to agree on the final storage mechanism before `HazardSystem`'s caching layer is finalized.
2. **`HazardTransformerPostCustom.StackKey`'s arbitrary-NBT-sensitive keying** (the `respectNbt=true` path) has no clean Data Component translation, since Data Components are typed/named fields, not "the rest of whatever NBT happens to be on the stack." Recommend keeping this specific mechanism's storage on NBT-equivalent custom data (NeoForge 21.1 still supports a generic `DataComponents.CUSTOM_DATA` compound-tag component for exactly this "arbitrary addon data" use case) rather than forcing it into named components - needs an explicit decision, not a silent default.
3. **Exact NeoForge 21.1 event names for the two hook points CE relies on ASM for** (per-tick dropped-item hazard update, and per-slot inventory-change detection for the delta-scan fast path) were not confirmed against a live working example in the Neo Edition reference tree (it doesn't implement either optimization) or elsewhere in this task's read scope. Do not implement these two hook points from guessed event names; a follow-up grep across the full Neo Edition tree (outside the `hazard` package, e.g. its event-handler classes) or NeoForge's own event package listing is needed before writing `HazardSystem`'s tick/delta wiring.
4. **Fluid-handler capability accessor name** for `HazardTransformerForgeFluid`'s port (`Capabilities.FluidHandler.ITEM` or equivalent) should be confirmed against a real usage in the Neo Edition tree outside the `hazard` package (e.g. wherever Neo Edition's own fluid-container items are implemented) before implementation, per the "never guess NeoForge APIs" hard rule - not confirmed within this task's read scope.
5. **AE2 compat** (`HazardTransformerRadiationME`) depends entirely on Applied Energistics 2's own 1.21 API, which is outside this task's and this repo's knowledge; treat as best-effort/deferred, not a Phase 0/1 blocker.
6. **Interface vs. abstract class for `IHazardType`/`IHazardModifier`/`IHazardTransformer`.** CE explicitly refactored all three from abstract classes to interfaces (see the "mlbv: made it an interface to be more flexible" comments) - this plan preserves that CE-side design decision even though the existing (partial) Neo Edition port made the opposite choice (abstract classes) for its own equivalents. Flagging in case the integration step wants stack consistency with the already-partially-written Neo Edition-style code instead of literal CE parity - this is a judgment call, not a correctness issue either way.

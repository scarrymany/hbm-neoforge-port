## Headline finding

1. **This exact scope was already covered at survey depth by `docs/phase3/armor_equippable_framework.md`** (published earlier this phase) — its Phase-3-safe-scope table already lists `ArmorFSB`, `ArmorFSBPowered`, `ArmorFSBFueled`, and all 5 `Jetpack*` classes, and its Key design/API decisions #7 already proposes `hbm:armor_charge`/`hbm:jetpack_fuel` Data Components. **This report does not re-litigate that base-class hierarchy or the `ArmorItem`/`Item.inventoryTick`/`IClientItemExtensions` API shapes it already confirmed** — those stand. What this report adds, per this task's specific brief to read the 5 jetpack files and `ArmorFSB`/`ArmorFSBPowered` "in full": the exact charge/absorb-damage mechanic (which turns out **not** to be what the task assumed — see #2), a per-variant flight-physics table for all 5 jetpacks, and the `JetpackHandler`/`JetpackGlider` fuel-tank subsystem the survey-level report only mentioned in passing.
2. **"FSB" does not stand for "Force Shield Belt," and `ArmorFSB`/`ArmorFSBPowered` do not implement a damage-absorbing shield at all.** A CE source comment and every doc-comment in this class family calls it the **"full suit bonus"** base (confirmed literally: this port's own `docs/phase1/items_food_gear.md` line 96 independently arrived at the same reading, and CE's `ArmorFSB.java` header comment discusses "the original 1.7 version" of this *set-bonus* class, never a shield). `ArmorFSBPowered.charge`/`ArmorFSBFueled.fuel` are a **battery/fuel gate on the whole armor set's set-bonus effects** (`isArmorEnabled(stack) = getCharge(stack) > 0`, consumed by `ArmorFSB.hasFSBArmor`'s per-piece `isArmorEnabled` check) — not damage absorption, and not decremented by incoming hits at all; `setDamage(ItemStack, int)` drains it, called by vanilla's own durability-tick machinery (`stack.getItem().setDamage` is invoked wherever CE code calls `stack.damageItem(1, entity)`, which nothing in the 6 files read here actually does — the drain that matters in practice is `ArmorFSBPowered.onArmorTick`'s explicit `dischargeBattery(stack, drain)` once per tick when `drain > 0`).
3. **The real "absorb incoming damage, recharge over time" shield mechanic is a completely separate system**, keyed off `HbmCapability`'s (CE) / `HbmPlayerAttachment`'s (this port, **already ported, already correct**) `shield`/`maxShield` float fields — populated by `ItemFlask` (already ported, Phase 1) and `ItemModShield` (a `kevlar`-slot `ItemArmorMod` insert, not FSB-related), decremented in `ModEventHandler.onEntityHurt` (a plain `LivingHurtEvent` listener, nothing to do with any `Item` class), and passively regenerated in `EntityEffectHandler.onUpdate` (also nothing to do with `ArmorFSB`). **`ItemFusionCore` does not recharge this shield either** — it recharges `ArmorFSBPowered`'s battery `charge` field (and any other `IBatteryItem` worn), via `Library.chargeBatteryIfValid` (already ported, confirmed). The task's framing conflated these two independent mechanics; this report documents both, correctly separated, since a Phase 3 implementer would otherwise wire `ItemFusionCore` to the wrong field.
4. **The 5 `Jetpack*` items are dual-mode: standalone chestplate *or* mod-slot insert into another chestplate.** All 5 extend `JetpackBase`/`JetpackFueledBase extends ItemArmorMod` (type `ArmorModHandler.plate_only`), so any of them can be crafted into another chestplate's mod-slot 1 via the (Phase-3-armor-table-gated) armor-mod system, in which case `ItemArmorMod.modUpdate`/`modRender` delegate straight into the same `onArmorTick`/`getArmorModel` used when the jetpack is worn directly in the chest slot (`JetpackBase.addInformation` literally prints "Can be worn on its own!"). **`JetpackGlider` is the one exception**: it extends `ItemArmorMod` directly (not `JetpackBase`), so it is mod-slot-**only** — it has no `isValidArmor`/`getArmorModel` override and cannot be worn as a chestplate by itself; it must be inserted into a real chestplate's mod slot to do anything, and that chestplate's own `modUpdate`→`JetpackHandler.hasJetpack`/`getTank` plumbing is what actually flies the player.
5. **Two entirely separate jetpack flight engines exist in CE, and only one is reachable from the 5 files this task named.** `JetpackRegular`/`JetpackBreak`/`JetpackBooster`/`JetpackVectorized` each implement their own tiny `onArmorTick` physics inline (a handful of `motionY +=`/`motionX +=` lines, detailed in the table below) gated on `HbmCapability.getData(player).isJetpackActive()` — this maps directly onto the already-ported, already-confirmed-working `HbmPlayerAttachment.isJetpackActive()`. `JetpackGlider`, by contrast, has **no** `onArmorTick` of its own at all (it only implements the fuel-tank `IFillableItem` contract) — its actual flight logic lives entirely in `JetpackHandler` (1,075 lines: client-side `InputUpdateEvent` interception with hover/direct-thrust modes, a server-side `perPlayerInfo` map keyed by identity, its own `JetpackSyncPacket`, and a large HUD/particle/rendering block), which this port has **not yet ported any of** and which `hasJetpack(EntityPlayer)`/`getTank`/`setTank` gate specifically on `ModItems.jetpack_glider` being in mod slot 1 — i.e. `JetpackHandler` is `JetpackGlider`'s exclusive delivery mechanism, structurally unrelated to the other 4 jetpacks' `HbmPlayerAttachment.isJetpackActive()` path.

### Per-jetpack flight-physics reference table

All 5 variants gate their entire tick body on `getFuel(stack) > 0`; all decrement fuel via `useUpFuel(player, stack, rate)` = "every `rate` ticks, `fuel -= 1`" (an *integer mB-per-tick-batch* drain, not a per-tick float). `Vec3NT.createVectorHelper(...).length()` is just `Math.sqrt(x²+y²+z²)` (CE's own vector-math wrapper, no port-side equivalent needed beyond `Vec3.lengthSqr()`/`Math.sqrt`).

| Variant | Fuel type / capacity | Activation gate | Vertical thrust | Lateral | Fuel rate (ticks per −1 fuel) | Notes |
|---|---|---|---|---|---|---|
| `JetpackRegular` | KEROSENE / 12000 | `isJetpackActive()` | `motionY += 0.1` while `motionY < 0.4`; `fallDistance = 0` | none | 5 | Simplest — pure vertical clamp-and-thrust. |
| `JetpackBreak` | KEROSENE / 12000 | **active**: `isJetpackActive()`; **passive**: `!sneaking && !onGround && enableBackpack` | active: `motionY += 0.1` while `<0.4`; passive: tiered clamp (`motionY += 0.2` if `<-1`, `+= 0.1` if `<-0.1`, `= 0` if `<0`) | none | active: 5; passive: 10 (cheaper) | The only variant with a no-input auto-glide mode; both branches call `ArmorUtil.resetFlightTime` (anti-kick "flying" flag reset) and `fallDistance = 0`. |

## Deferred scope

- **`JetpackHandler`'s entire flight/HUD/particle engine (1,075 lines)** — this is `JetpackGlider`'s sole delivery mechanism (Headline #5) and is out of this report's Phase-3-safe claim for one concrete, narrow reason: it is almost entirely **client input handling + rendering** (`InputUpdateEvent`, `renderHUD`, `preRenderPlayer`/`postRenderPlayer`, a custom `LayerRenderer<EntityPlayer>`, `ParticleJetpackTrail`/`ParticleFakeBrightness`/`ParticleHeatDistortion`/`ParticleRocketPlasma` spawning, `MovingSoundJetpack`), which is Phase 5 (Client & UX) per this port's own phase boundary — the same boundary `docs/phase3/armor_equippable_framework.md` already drew for every other armor-item's `Model`/render hook. **What Phase 3 can and should port now**: the server-authoritative pieces that are pure logic, not rendering — `hasJetpack`/`getTank`/`setTank` (mod-slot lookup, trivial once `ArmorModHandler` exists), `getSpeed(FluidType)`/`getDrain(FluidType)` (the two per-fuel constant tables, pure functions), and `serverTick()`'s drain-the-tank loop (`tank.drain(ceil(getDrain(type) * thrust))` once per active player per tick) — leaving `JetpackInfo`'s client-only fields (`animTime`, `particleSpawnPositions`, the 3 particle lists, `sound`) and every `@SideOnly(Side.CLIENT)` method as a named Phase 5 follow-up, exactly like this port's existing pattern of shipping a server-only item shell ahead of its renderer.
- **`JetpackSyncPacket`** (referenced throughout `JetpackHandler` for `JetpackInfo` state sync) needs a `CustomPacketPayload` following `HbmNetwork`'s confirmed-live pattern (`record ... implements CustomPacketPayload` + `StreamCodec` + `registrar.playToClient(...)`, exactly the shape the one real payload already registered there — `BufPacket` — demonstrates) once the server-authoritative half of `JetpackHandler` above is ported. Not designed here since it only matters once that server-tick loop exists; `docs/phase3/armor_equippable_framework.md` open question #6 already flags this same needed packet from the armor-framework side — this is the same packet, not a second one.
- **Jetpack particle VFX on the 4 non-Glider variants** (`AuxParticlePacketNT`/`HbmEffectNT.Jetpack`, fired from each `onArmorTick` while active) needs Phase 2's particle-packet system, confirmed as a real forward reference by `docs/phase1/items_food_gear.md`'s own jetpack note. Port the tick logic's *physics* now with the particle-spawn call left as a documented forward-reference TODO (same "physics now, particle later" split `docs/phase2/rbmk_reactor.md` used for meltdown byproducts) — do not silently drop the call site or invent a stand-in effect.
- **`ArmorFSB.onArmorTick`'s geiger-sound branch** (`ContaminationUtil.getActualPlayerRads`, `ArmorFSB.check` → `ChunkRadiationManager.proxy.getRadiation`) is Phase 4 (world/radiation simulation) per `docs/phase0/STATUS.md`, already flagged identically by `docs/phase3/armor_equippable_framework.md` deferred-scope entry #3 for the same class — not re-derived, just reconfirmed relevant to this narrower report's exact file list.
- **`ArmorFSB.handleFall`'s hard-landing knockback** (`player.world.getEntitiesWithinAABBExcludingEntity` + `attackEntityFrom(DamageSource.causePlayerDamage(player).setDamageBypassesArmor(), ...)`) needs a real `DamageSource` built via `level.damageSources().playerAttack(player)`-equivalent with bypass-armor semantics; this is ordinary vanilla-damage-source construction (not a new `ModDamageTypes` entry — confirmed by reading `com.hbm.damage.ModDamageTypes`, which has no "hard landing" or generic player-melee entry, because CE itself uses the *vanilla* player-damage source here, not a custom one) — flagged only so an implementer doesn't go hunting for a nonexistent custom damage type.
- **The battery-charge and fuel-amount Data Components** (`hbm:armor_charge` long, `hbm:jetpack_fuel` int) are already specified by `docs/phase3/armor_equippable_framework.md` decision #7, following the exact `hbm:bonus_radiation`/`hbm:unstable_decay_timer` precedent from `docs/phase0/hazard.md`. `JetpackGlider`'s `FluidTankNTM`-in-NBT needs its own component wrapping `{FluidType, fill, maxFill}` — that report already flags this as "reuse whatever shape the fluid system area settles on," which this report reconfirms rather than re-derives; do not invent a jetpack-specific fluid-item component in isolation from whatever other fluid-holding items (e.g. `ItemCanister`, `ItemFluidContainerInfinite` from `docs/phase1/items_tool.md` bucket (a)) end up using.

- **`ItemPancake`** (named by `docs/phase1/items_food_gear.md` as blocked on `ArmorFSB.hasFSBArmorIgnoreCharge` existing) unblocks the moment this package's `ArmorFSB` lands — already flagged identically by `armor_equippable_framework.md`'s deferred scope; reconfirmed, not re-owned by this report.

## Key design/API decisions

Confirmed from real code read in this survey (CE for behavior; this port's own committed code, and Neo Edition only for confirmed 1.21.1 API shape — no NeoForge API invented below):

- **The shield mechanic and the FSB battery/fuel mechanic are two independent systems and must stay that way in the port.** Do not let `ItemFusionCore`'s implementation reach for `HbmPlayerAttachment.setShield` (wrong field) — it must call whatever this port's Phase 3 port of `Library.chargeBatteryIfValid`-consuming logic looks like against `IBatteryItem`/`ArmorFSBPowered`'s charge component. Conversely, `ArmorFSB`/`ArmorFSBPowered`/`ArmorFSBFueled` need **no** shield-related code at all — the capability layer they need (`isArmorEnabled`, `hasFSBArmor`, dash/stamina) has already been fully identified in the tables above, and none of it touches `shield`/`maxShield`.
- **`HbmPlayerAttachment` needs zero new fields or methods for this scope.** Every accessor CE's `ArmorFSB`/jetpack/shield code paths need already exists, already named identically to CE, and is already exercised by the already-ported `ItemFlask`. This is a rare case in this port's Phase 1→3 history where the capability layer was built *ahead* of the content that needs it (confirmed by the pre-existing `import com.hbm.items.armor.ItemModShield` forward reference sitting in `HbmPlayerAttachment.getEffectiveMaxShield` before this armor package even existed).
- **`JetpackBase`/`JetpackFueledBase`'s dual armor-slot/mod-slot delivery is a real design constraint, not an implementation detail to simplify away.** A jetpack `ArmorItem` must both (a) declare a normal chest-slot `ArmorItem.Type.CHESTPLATE` registration so it can be worn directly, and (b) extend/implement whatever this port's ported `ItemArmorMod` becomes (type `PLATE_ONLY`) so it can be installed as slot-1 mod into an unrelated chestplate — `ItemArmorMod.modUpdate`/`getModifiers`-equivalent must delegate to the exact same tick method the standalone-wear path uses (CE achieves this by literally calling `onArmorTick` from both `Item.inventoryTick` — standalone — and `modUpdate` — as a mod), not two divergent implementations.
- **`JetpackGlider` is armor-mod-only and must not be given a standalone `ArmorItem.Type`.** Confirmed by CE never overriding `isValidArmor`/`getArmorModel` on it (unlike every other `Jetpack*` class, which does) — porting it as a wearable chestplate in its own right would be a behavior change from CE, not a simplification.
- **`ArmorModHandler`'s 9-slot mod storage**: follow `docs/phase3/armor_equippable_framework.md` decision #6 exactly (`TagsUtil`-backed `CustomData`, `ItemStack.parse`/`.save(registryAccess, tag)`) — this report re-confirms it applies identically to jetpack mod-slot storage, since jetpacks are `ItemArmorMod` subclasses like any other insert.
- **Two Data Component types this report's scope specifically needs** (beyond the two `armor_equippable_framework.md` already named): none — `hbm:armor_charge` (long) and `hbm:jetpack_fuel` (int) fully cover `ArmorFSBPowered.charge` and every `JetpackBase`/`JetpackFueledBase.fuel` field; `ArmorFSBFueled.fuel` (an int mB amount, distinct field, same *shape*) can reuse `hbm:jetpack_fuel`'s int-codec pattern under its own registered id (e.g. `hbm:armor_fuel`) rather than sharing the literal jetpack-named component across two unrelated item families — a naming call, not a new design.
- **Explosion/block-removal batching** (PORT_SPEC's explicit "batched LevelChunk section writes + deferred lighting" instruction): **does not apply to this report's scope.** Nothing in `ArmorFSB`, `ArmorFSBPowered`, `ArmorFSBFueled`, `JetpackBase`, `JetpackFueledBase`, `ItemArmorMod`, `ArmorModHandler`, `JetpackHandler`, or any of the 5 `Jetpack*` items removes, places, or iterates world blocks in bulk (`ArmorFSB.handleFall`'s hard-landing effect only pushes/damages nearby *entities*, never touches blocks). Noted explicitly, as instructed, rather than silently omitted — this instruction's real target is the explosion-engine package (`docs/phase3/explosion_engine.md`), not this one.

## Open questions / risks

1. **`ArmorFSBPowered.setDamage`/`ArmorFSBFueled.setDamage` overrides `Item#setDamage`, a vanilla durability-bar hook, to instead drain the battery/fuel field** — CE relies on this being called wherever vanilla or CE code calls `stack.damageItem(amount, entity)`. Nothing in the 11 files read for this report actually calls `damageItem` on an FSB-powered/fueled piece (the real drain path is `onArmorTick`'s explicit `dischargeBattery`/`setFill` call), so this override may be dead code in practice for these two classes specifically — worth a targeted grep across the ~13/2 concrete leaves (out of this report's scope) before assuming it needs a faithful `Item#hurtAndBreak`-hook port versus being droppable. Flagged, not resolved, since those leaf classes belong to the sibling armor-framework reports.
2. **`resetFlightTime(EntityPlayer)`** (`mp.connection.floatingTickCount = 0`, called by 3 of the 5 jetpack variants plus `JetpackHandler`) is a 1.12-Forge-mapped field name on `NetHandlerPlayServer`. This report did not verify the exact Mojang-mapped 1.21.1 field name on `ServerGamePacketListenerImpl` (anti-cheat "is the player illegally floating" tick counter) — neither this port's own source nor Neo Edition's `ArmorUtil`/`DamageResistanceHandler` contains an equivalent call, so there is no confirmed precedent in either reference tree. Needs a direct check against real 1.21.1 Mojang mappings before implementation; do not guess the field name.
3. **`ArmorFSBPowered`'s zero-direct-instantiation status** (confirmed by `grep -c "new ArmorFSBPowered(" — 0` across all of CE) means this report's claims about its exact behavior rest entirely on reading the class definition itself, not on any concrete configured instance's constructor arguments (`maxPower`/`chargeRate`/`consumption`/`drain` values). Real tuning numbers for the ~13 concrete leaves that do instantiate it belong to whoever implements those leaves (`armor_equippable_framework.md`/`armor_special_sets.md`'s scope), not this report.
4. **`JetpackGlider.capacity` is currently hardcoded to `-1` in its constructor signature's `i` parameter** (`new JetpackGlider(MaterialRegistry.aMatSteel, -1, EntityEquipmentSlot.CHEST, 20000, "jetpack_glider")` — the real capacity is the *next* constructor argument, `20000`; `i` itself is read but never stored or used inside `JetpackGlider`'s body at all, confirmed by reading the full 125-line file). This is very likely CE dead-parameter cruft (an unused armor-durability argument left over from an earlier version of the constructor) rather than a meaningful `-1` sentinel — worth a quick double-check against CE's git blame/other `ItemArmorMod` constructors at implementation time, but not something this report can resolve by static reading alone.
5. **`JetpackBreak`'s passive-glide branch reads `props.getEnableBackpack()`** (this port's `HbmPlayerAttachment.getEnableBackpack()`, confirmed present and behaviorally identical to CE's toggle) — worth double-checking during implementation that this flag's *default* value (`true` in this port's field initializer, matching CE) doesn't make brand-new characters wearing a `JetpackBreak` auto-glide by default before they've ever pressed the jetpack-toggle keybind; this is CE's actual default behavior (confirmed by reading the field initializer), not a port bug, but easy to mistake for one during QA.

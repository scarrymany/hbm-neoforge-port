
# Research report — mrec-13-arcfurnace-misc

Scope: three CE per-machine recipe-data classes under `upstream/hbm-ce/src/main/java/com/hbm/inventory/recipes/` — `ArcFurnaceRecipes.java` (302 lines), `CustomMachineRecipes.java` (154 lines), `BlastFurnaceRecipesNT.java` (105 lines). All three are cited by name in `docs/phase6/PARITY_REPORT.md` §3.7 and `docs/phase6/recipe_graph_audit.md` §2 point 3 as part of the ≈63 CE machine-recipe classes this port has zero data for. This is a research-only task; no implementation code was written.

## Scope confirmed

- **`ArcFurnaceRecipes.java`** — 302 lines, read in full. `com.hbm.inventory.recipes.ArcFurnaceRecipes extends SerializableRecipe`. Structure: one `registerDefaults()` method (lines 39–116) that is **not** a flat list — it is four distinct sub-patterns stitched together:
  1. **11 hand-written literal calls** (lines 41–53): silica-family ore-dict inputs (sand, flint, quartz gem/dust/block, fiberglass ingot/block, asbestos ingot/dust/block) → `nugget_silicon` (solid) + `Mats.MAT_SILICON` (fluid), plus one glass-conversion recipe (`sand_quartz` block → `glass_quartz` block, solid-only) and one borax→boron recipe.
  2. **A `for` loop over `ItemBedrockOreNew.BedrockOreType.VALUES`** (lines 55–71), 11 `register(...)` calls per iteration (6 solid byproduct/roasted→arc recipes, 3 fluid-only primary/crumbs recipes, 3 fluid-only washed-acid recipes) — this is the single largest literal-call-count contributor once the type count is known.
  3. **Autogen loop #1** (lines 74–91): `for (NTMMaterial material : Mats.orderedList) { for (MaterialShapes shape : MaterialShapes.allShapes) { ... } }` — a genuine nested table-driven loop, registers one fluid-only recipe per (material, non-`noAutogen` shape) pair **whose ore-dict name actually exists** (`OreDictionary.getOres(name)` non-empty gate), converting into `material.smeltsInto` at a ratio derived from `material.convIn`/`convOut`.
  4. **Autogen loop #2** (lines 93–100): iterates `Mats.materialOreEntries` (tag-keyed) and `Mats.materialEntries` (exact-item-keyed) — CE's Crucible/`MatDistribution` curated cast-material tables — calling `addCustomSmeltable` for each, which filters to only `SmeltingBehavior.SMELTABLE` members and registers one fluid-output recipe per entry key.
  5. **Autogen loop #3** (lines 102–115): iterates vanilla `FurnaceRecipes.instance().getSmeltingList()` and registers a solid-only Arc Furnace recipe for any furnace recipe whose input or output appears in `OreDictManager.arcSmeltable` (a hand-curated ~20-entry `HashSet` of vanilla ore/ingot/block items, defined elsewhere in `OreDictManager.java`, not this file).
  Plus helper methods: `register()` (occupied-input collision guard — dedupes such that only the first-registered recipe for a given resolved `ItemStack` input wins per solid/liquid channel), `addCustomSmeltable()`, `getOutput()`, `getSolidRecipes()`/`getFluidRecipes()` (JEI/lookup accessors), and the full `SerializableRecipe` JSON read/write pair (`readRecipe`/`writeRecipe`) for its on-disk-config-override mechanism. The `ArcFurnaceRecipe` inner class (lines 280–301) is the recipe-shape POJO: `Mats.MaterialStack[] fluidOutput` + `ItemStack solidOutput`, i.e. **one input → up to two independent outputs (a solid item AND/OR a set of molten materials), no single-output assumption**.

- **`CustomMachineRecipes.java`** — 154 lines, read in full. `com.hbm.inventory.recipes.CustomMachineRecipes extends SerializableRecipe`. Structure: a `Map<String, List<CustomMachineRecipe>>` keyed by machine-config name (CE's "Custom Machine" is a **single generic multiblock/TE whose recipe set is chosen per-placed-instance via a `recipeKey` string**, not a fixed machine type — see `CustomMachineConfigJSON.java`/`BlockCustomMachine.java` in CE, not read in full since out of this task's file list but named for context). `registerDefaults()` (lines 30–44) hardcodes **exactly one entry**, keyed `"paperPress"`: input 250mB water + 1 `powder_sawdust` → output 3 vanilla `Items.PAPER` (100% chance, encoded as `Pair<ItemStack,Float>` with `1F`), 60-tick duration, 10/tick fluid consumption, `"SOOT"` pollution type at 0.03/tick, zero radiation/flux/heat. This is **not a loop-generated file** — it is a single hardcoded literal recipe registered into a keyed map structure that in CE is populated far more heavily by user-authored JSON under `config/hbm/customMachines/` at runtime (the `readRecipe`/`writeRecipe` pair, lines 62–135, is the actual bulk-loading path; `registerDefaults()` is only the one built-in fallback). The `CustomMachineRecipe` inner class (lines 137–152) is the general recipe shape: `FluidStack[] inputFluids`, `AStack[] inputItems`, `FluidStack[] outputFluids`, `Pair<ItemStack,Float>[] outputItems` (**chance-weighted, multi-output**), plus `duration`, `consumptionPerTick`, `pollutionType`/`pollutionAmount`, `radiationAmount`, `flux`, `heat`.

- **`BlastFurnaceRecipesNT.java`** — 105 lines, read in full. `com.hbm.inventory.recipes.BlastFurnaceRecipesNT extends GenericRecipes<BlastFurnaceRecipe>` (CE's generic 9-recipe-class loader shape, same base `GenericRecipes<T>` this port already carries a compile-stub version of — see below). `registerDefaults()` (lines 30–83) is a **flat list of 15 hand-written literal `register(...)` calls**, no loops, no material-table iteration — genuinely small/enumerable. Each recipe: 2 item inputs (via `OreDictStack`/`ComparableStack`), 1–2 item outputs, an explicit per-recipe `duration` (400–1,200 ticks). `inputItemLimit()=2`, `outputItemLimit()=2`, both fluid limits `0` — this machine is strictly item-in/item-out, no fluids at all (simpler shape than ArcFurnace or CustomMachine). `getRecipe(ItemStack s0, ItemStack s1)` (lines 90–104) does order-independent 2-slot matching against `recipeOrderedList`. `BlastFurnaceRecipe.java` (the referenced inner recipe class, 23 lines, also read) is a thin `GenericRecipe` subclass adding nothing but a NEI-tooltip override — no extra fields beyond what `GenericRecipe` already carries (name/duration/pools/icon).

All three files confirmed **NOT touched by this port at all** — grep for `arcfurnace`/`arc_furnace`/`ArcFurnace`, `custommachine`/`CustomMachine`/`paperPress`/`paper_press`, and `blastfurnace`/`blast_furnace`/`BlastFurnace` across `src/main/java/com/hbm` and `src/main/resources` returns **zero hits** for ArcFurnace and CustomMachine anywhere, and for BlastFurnace returns only three unrelated hits (an `AdvancementManager` field name, a language-provider achievement string, and one advancement JSON — see next section).

## Already covered by this port

**None of the three recipe files' actual recipe data is covered.** This is a genuine hard-zero gap for all three, not a partial-coverage case — confirmed by direct grep (above) and by the absence of any corresponding machine block/block-entity (below). There is nothing to diff against.

One adjacent, load-bearing finding worth flagging precisely rather than folding into "not covered": **`src/main/resources/data/hbm/advancement/achblastfurnace.json` already exists** (part of the 65/65 advancement-count parity §3.8 of the parity report celebrates) and its `display.icon.id` and its `crafting_hbm_machine_blast_furnace` trigger condition both reference item id **`hbm:machine_blast_furnace`** — but that item/block id **does not exist anywhere in this port's Java** (grepped `src/main/java/com/hbm` for `machine_blast_furnace`: zero hits). This advancement is currently dead — it can never fire and its icon will render as a missing-item placeholder — until the Blast Furnace machine block itself is built. This is a small, concrete, previously-undocumented gap this task found; noted here so the implement wave building the Blast Furnace block picks the exact same registry id the advancement JSON already expects.

The port's `com.hbm.inventory.recipes.loader.GenericRecipe`/`GenericRecipes` classes (105+59 lines, both read in full) are explicitly **not** the real machine-recipe shape — their own class javadocs say so directly: `GenericRecipe.java`'s header states it is "a minimal compile-time stand-in" carrying only the slice `ItemBlueprints`/`ItemBlueprintFolder` need (name/pool/localization bookkeeping), and names `BlastFurnaceRecipesNT`'s parent shape as one of the "9 recipe classes" whose real input/output/duration/power fields are explicitly **not** ported here — "whoever ports a real GenericRecipe-shaped machine... should extend or replace this." So this is a **documented placeholder acknowledging the gap**, not partial coverage of `BlastFurnaceRecipesNT`'s content — `BlastFurnaceRecipesNT` does NOT currently extend the port's `GenericRecipes` (that class isn't even generic/parameterized in the port), and none of its 15 recipes exist in any form.

### ArcFurnaceRecipes — entry count and representative sample (NOT a small enumerable file — multiplicative)

**Exact literal call-site count:** 11 hand-written (silica/glass/borax family, lines 41–53) + up to 11 calls **per** `BedrockOreType` inside the bedrock loop (lines 55–71) + 1 call per (material × non-`noAutogen` shape) pair that clears the ore-dict-existence gate (lines 74–91) + 1 call per `Mats.materialOreEntries`/`materialEntries` key (lines 93–100, **currently 0 in CE's committed defaults too** — these maps are populated by CE's `MatDistribution` JSON, not by this file, so this sub-pattern's real count is data-driven, not visible from this Java file alone) + 1 call per vanilla-furnace-recipe entry whose input/output intersects `OreDictManager.arcSmeltable` (lines 102–115, bounded by vanilla's own smelting list ∩ a ~20-entry curated set — small, single digits to low tens).

The multiplicative core is the bedrock loop and the material-shape autogen loop:
- **Bedrock loop**: `ItemBedrockOreNew.BedrockOreType.VALUES.length` × 11 recipes/type. This port's `BedrockOreItems.java` census (per `docs/phase6/recipe_graph_audit.md` §4) is "157 items... 6 `BedrockOreType` × 26 `BedrockOreGrade` + 1 base item" — so **CE's `BedrockOreType` has 6 members**, giving **66 recipes** from this loop alone.
- **Material-shape autogen loop**: bounded by `Mats.orderedList.size() × MaterialShapes.allShapes.size()` before the ore-dict-existence gate; this port's `Mats.java` carries "the same ~90 MAT_* constants" (per its own header) and `MaterialShapes.java` defines **31** `MaterialShapes` constants (counted directly from the file read above: QUANTUM, NUGGET, TINY, FRAGMENT, DUSTTINY, WIRE, BOLT, BILLET, INGOT, GEM, CRYSTAL, DUST, DENSEWIRE, PLATE, CASTPLATE, WELDEDPLATE, SHELL, PIPE, QUART, BLOCK, HEAVY_COMPONENT, PART, LIGHTBARREL, HEAVYBARREL, LIGHTRECEIVER, HEAVYRECEIVER, MECHANISM, STOCK, GRIP, plus ANY/ONLY_ORE/ORE/ORENETHER which are `noAutogen()`-flagged and thus excluded) — the real emitted count depends on which (material, shape) ore-dict names actually resolve in CE's registered-item set, not knowable without running CE, but the **structural bound is ~90 × ~27 ≈ 2,400 candidate pairs, gated down by real ore-dict existence** — CE's actual emitted count is almost certainly a small fraction of that bound (most materials don't have every shape as an ore-dict-registered item), consistent with why this task cannot give a single exact number for this sub-pattern without a live CE registry dump.

**Generating pattern for an implement-wave table-driven Java loop** (matching `ModRecipeProvider`'s `BILLET_SETS`/`MINERAL_SETS` convention): this file does **not** reduce to one clean loop the way CE's own material/shape autogen loops do, because it is itself 4 different generators. An implement-wave agent should structure it as 4 separate table-driven pieces mirroring CE's own structure exactly, rather than trying to unify them:
1. A **flat literal list** (11 entries) for the silica/glass/borax hand-written recipes — small enough to hand-transcribe directly as either JSON recipes or a short Java array-of-records, no loop needed.
2. A **nested loop over `BedrockOreType.VALUES`** emitting 11 recipes per type — directly portable as a Java `for` loop once `ItemBedrockOreNew`-equivalent `make()`/`toFluid()` helpers exist on this port's `BedrockOreItems`/`ItemBedrockOre` (currently absent, small addition).
3. A **nested loop over `(Mats.orderedList, MaterialShapes.allShapes)`** gated by ore-dict/tag existence — directly portable once this port has a tag-existence check equivalent to CE's `OreDictionary.getOres(name).isEmpty()` (1.21's analog: check whether `TagKey<Item>` `shape.commonTag(material)` has any entries via `ItemTags`, or simpler: check `MaterialItemGenerator`'s own registered-item set for that (material,shape) pair since this port already tracks which shapes each material auto-generates via `setAutogen(...)`).
4. The **`Mats.materialOreEntries`/`materialEntries` loop** and the **vanilla-furnace-intersection loop** are both **structurally blocked** until, respectively, Crucible/`MatDistribution` populates those maps (loop 4a) and an `OreDictManager`-equivalent curated vanilla-ore set exists (loop 4b, small — ~20 hardcoded `ComparableStack`s, portable standalone without waiting on Crucible).

## Machine block/block-entity existence check

**None of the three machines exist in this port at any level** (block, block entity, GUI, container) — confirmed by directory listing of `src/main/java/com/hbm/blockentity` (top-level dirs: `bomb`, `machine`, `machine/chem`, `machine/fusion`, `machine/oil`, `machine/rbmk`, `turret`, `network`, `network/energy` — no arc-furnace/blast-furnace/custom-machine subfile) and `src/main/java/com/hbm/blocks/machine` (21 files listed, e.g. `MachineShredderBlock`, `MachineCrystallizerBlock`, `MachineRefineryBlock`, `MachineMixerBlock` — none named Arc/Blast/Custom). CE's own machine block/TE/GUI/container files for cross-reference: `MachineArcFurnaceLarge.java` + `TileEntityMachineArcFurnaceLarge.java` + `GUIMachineArcFurnaceLarge.java` + `ContainerMachineArcFurnaceLarge.java`; `MachineBlastFurnace.java` + `TileEntityMachineBlastFurnace.java` + `GUIBlastFurnace.java` + `ContainerBlastFurnace.java`; `BlockCustomMachine.java` + `TileEntityCustomMachine.java` + `ItemCustomMachine.java` + `CustomMachineConfigJSON.java`. **This means the implement wave for this assignment cannot ship working recipes alone — the machine block+block-entity is a co-requisite for all three**, unlike some of this port's already-ported machine types (Crystallizer, Mixer, Refinery, Shredder) where the block/TE already existed and only recipe data was the gap. The one exception where recipe-only work has standalone value: none of these three, since none has a block/TE. (Contrast: the `achblastfurnace.json` advancement finding above shows the Blast Furnace's *registry id* was anticipated/reserved even though nothing else about it exists yet — a signal, not a substitute, for building it.)

## Recommended 1.21.1 implementation shape

- **Blast Furnace (`BlastFurnaceRecipesNT`)**: **Custom `Recipe<?>`/`RecipeSerializer` class**, not plain JSON shaped/shapeless — needs order-independent 2-item-slot matching (`getRecipe(s0,s1)`'s own logic tries both orderings) and a per-recipe `duration` field vanilla's `Recipe` contract doesn't carry. This is the **exact same shape** this port's own `BreederRecipe.java` already establishes end-to-end (single/paired `Ingredient` in, single `ItemStack` out, one extra numeric field, registered via `HbmRecipes.RECIPE_TYPES`/`RECIPE_SERIALIZERS` append, `MapCodec`+`StreamCodec` pair) — a `BlastFurnaceRecipe` class following `BreederRecipe`'s file-for-file pattern (2 `Ingredient`s instead of 1, `duration` instead of `flux`, output up to 2 `ItemStack`s instead of 1) is the direct, low-risk path; do not invent a new registration convention. JSON shape: `{"input": [ingredient, ingredient], "output": [itemstack, itemstack?], "duration": n}`, one file per recipe under `data/hbm/recipe/blast_furnace/` (15 files, or table-driven where the steel/copper families share structure — 9 of the 15 fall into two clean 4-5-entry families: `steelFrom{Ingot,Dust,Ore}`+`steelWithFlux`, and `mingrade{,Dust,Ingot,Cursed,Ore}` — could be a small Java table generating those 9 plus the 6 remaining hand-authored, mirroring `ModRecipeProvider`'s `ONE_TO_NINE_PAIRS`-style convention).
- **Custom Machine (`CustomMachineRecipes`)**: Given the real content is player/pack-authored runtime JSON keyed by an arbitrary `recipeKey` string (not a fixed recipe corpus), and the recipe shape needs multi-fluid I/O + chance-weighted multi-item-output + pollution/radiation/flux/heat side-effect fields, this needs a **bespoke `Recipe<?>` class with a richer codec** than `HbmSimpleRecipe`/`BreederRecipe`'s single-in/single-out shape — closer in spirit to this port's already-noted "tier 2+" machine-recipe design referenced by `HbmSimpleRecipe.java`'s own javadoc (`docs/phase2/items_tool_machine_coupling_and_recipe_system.md` Part B). Given it's a **generic** machine (recipe set chosen per placed block instance via `recipeKey`, not per machine type), the 1.21 shape most likely needs its own `RecipeType` per configured machine variant, or a single `RecipeType` filtered by a `recipeKey` field read from the block entity — an open design question genuinely worth flagging to whoever picks this up (see below). The one hardcoded default recipe (`paperPress`) is trivial to encode once the class exists.
- **Arc Furnace (`ArcFurnaceRecipes`)**: Needs a **custom `Recipe<?>`** with `Ingredient` in, **up to two independent outputs** (an `Optional<ItemStack>` solid AND/OR a `List<Mats.MaterialStack>` fluid/molten output) — closer to `CustomMachineRecipes`' richness than `BreederRecipe`'s simplicity, though without the pollution/radiation/heat fields. The `Mats.MaterialStack` fluid-output shape is genuinely new relative to every recipe type this port has ported so far (`BreederRecipe`/`HbmSimpleRecipe` are both single-`ItemStack`-out only) — will need its own codec built from `Mats.matByName`/`NTMMaterial` (both already exist and are stable). The 4 sub-generators (hand-written / bedrock-loop / material-shape-autogen loop / Crucible-table loop / vanilla-furnace-intersection loop) should NOT all be forced into hand-authored JSON — the hand-written 11 and the vanilla-furnace-intersection subset (once `OreDictManager`'s ~20-entry `arcSmeltable` set is ported standalone) are small enough for JSON; the bedrock loop and material-shape-autogen loop should be **Java-side datagen loops** (following `ModRecipeProvider`'s own established convention of generating JSON at build time from a Java table) mirroring CE's own loop structure directly, since transcribing ~66+ bedrock recipes and a two-hundred-plus-candidate material×shape cross product by hand would be exactly the kind of hand-transcription error risk `ModRecipeProvider`'s existing `BILLET_SETS`/`MINERAL_SETS` convention was built to avoid. The Crucible-table loop (`Mats.materialOreEntries`/`materialEntries`) should simply be **left unimplemented until Crucible/`MatDistribution` lands** — it has zero real entries to generate from today regardless of how the recipe class itself is written.

## Open questions / risks

1. **Machine-block dependency is total for all three files.** This assignment is recipe-data research, but none of the three recipes are worth anything without their machine block+TE, and none of those exist. Whoever implements this needs to either (a) build all three machine blocks/TEs as a co-requisite (out of this task's scope, a Phase 2/8-shaped task), or (b) the recipe classes/JSON can still be authored and merged now as inert data waiting for the block, matching how this port's advancement JSON for Blast Furnace was apparently already authored ahead of its block (see the `achblastfurnace.json` finding). Recommend flagging this explicitly to whoever schedules the actual block-building work so the recipe data lands in the same phase, not stranded.
2. **`OreDictManager`'s absence is a genuinely new, previously-undocumented gap** (not called out by either Phase 6 doc) that blocks tag-based ingredient matching for potentially many more machine-recipe classes beyond just these two (any CE recipe class using `DictFrame.ingot()`/`.dust()`/`.ore()`/`.block()`-style calls, which is CE's dominant ingredient-matching idiom across essentially all of `com.hbm.inventory.recipes`). Worth surfacing to whoever is triaging the other ~60 unported recipe classes (sibling `mrec-*` tasks) as a shared, one-time small fix rather than each task rediscovering it independently — a single ~20-30 line class translating the handful of `DictFrame` constants these three files use into `MaterialShapes.commonTag(Mats.MAT_*)`-based `TagKey<Item>` lookups (plus the standalone `arcSmeltable` set) would likely unblock several sibling tasks at once.
3. **CustomMachine's per-instance `recipeKey` design is not fully resolved by this research.** CE's `BlockCustomMachine`/`TileEntityCustomMachine`/`CustomMachineConfigJSON` (not read in full — out of this task's named file list) would need reading before committing to a specific `RecipeType` strategy; flagged rather than guessed at.
4. **Material-shape autogen loop's true emitted count is not independently knowable without a live CE registry** (same caveat the Phase 6 parity report already applies elsewhere) — the ~90×~27 structural bound is real but the ore-dict-existence gate could cut it down substantially; an implement-wave agent generating this loop in Java (as recommended above) will get the CE-faithful count automatically by construction (the loop only fires when the tag/item actually resolves), so this is a research-limitation note, not a blocker to implementation.
5. **`ItemScraps.create(...)`'s signature already differs from CE's** (`create(ItemStack, int, boolean)` in this port vs. `create(Mats.MaterialStack, boolean)` in CE, per `ArcFurnaceRecipes.getFluidRecipes()`'s call shape) — not independently reconciled by this task; whoever wires Arc Furnace's fluid-output JEI/lookup accessor equivalent should check this port's actual `ItemScraps` call sites rather than assuming CE's shape carries over unchanged.

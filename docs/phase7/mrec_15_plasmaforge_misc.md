## Recommended 1.21.1 implementation shape

**None of the three files should become plain JSON vanilla-recipe-type recipes.** All three need custom recipe-data Java classes, following the precedent this port already established for its 9 existing bespoke machine-recipe classes (`com.hbm.inventory.recipes.{CrystallizerRecipes,MixerRecipes,RefineryRecipes}` and `com.hbm.inventory.recipes.chem.{CentrifugeRecipes,ChemPlantRecipes,CyclotronRecipes,GasCentrifugeRecipes,SILEXRecipes,ElectrolyserFluidRecipes}` — plain classes with a `register()`/`registerDefaults()` populating a static `Map`/`List`, matched by custom Java logic in the corresponding block entity, not by NeoForge's `RecipeType`/`RecipeSerializer`/`RecipeInput` machinery). Specifics:

- **GasCentrifugeRecipes: no new implementation work needed for the recipe-data half** — already done and verified faithful (see "Already covered" above). The only remaining work is (a) registering the 3 missing items (`fluorite`, `dust`, `nuclear_waste_tiny`) wherever this port's "simple standalone parts item" convention lives (e.g. alongside `PlateCrystalWasteItems`/`SpecialItems`, following the same `ItemBase`/`ItemCustomLore` pattern CE itself used), then wiring them into the two documented `TODO(items-followup)` substitutions in the port's own `GasCentrifugeRecipes.java` javadoc, and (b) — separately, a block-entity task, not a recipe task — porting the CE `IItemFluidIdentifier` tank-retyping mechanic to unblock the PUF6/WATZ legs via pipes.
- **PlasmaForgeRecipes: a new `PlasmaForgeRecipes` class in `com.hbm.inventory.recipes`, following the `ChemPlantRecipes`-shaped precedent exactly** (its own javadoc is close to a direct template: "up to N item inputs (each an `AStack`...), up to M fluid inputs, up to K item outputs... duration + power — as a plain static table"). CE's real shape needs: up to 12 `AStack` item inputs (the file's own `inputItemLimit()==12`), 1 fluid input, 1 item output, `duration`+`power`(energy) — a `PlasmaForgeRecipe` record/class with exactly those fields is a direct, low-risk translation. The `inputItemsEx` "expensive mode" alternate-ingredient leg (a CE config toggle, `GeneralConfig.enableExpensiveMode`) and the blueprint-pool (`setPools`/`setPools528`/`setPoolsAllow528`) / `setGroup` "auto-switch" mechanics are secondary CE progression/UX systems layered on top of the core recipe shape, **not** required for the recipe data itself to be useful — flag as an open question below rather than building them into a first pass, matching this port's own established precedent of dropping CE config-gated recipe variants without replacement (already done for the ore-dict compatibility legs in `ModRecipeProvider`'s own javadoc). Given the file is only 35 entries and the "weld" sub-family (10 entries) is the one genuinely regular loop-shaped part, hand-write the other 25 individually and loop only the weld family (see the compact table-driven pattern noted in the catalog section) — do not force the whole file into one generic loop.
- **ParticleAcceleratorRecipes: a new `ParticleAcceleratorRecipes` class, structurally closest to this port's own existing `CyclotronRecipes`** (`com.hbm.inventory.recipes.chem`, 83 lines) — same "2 inputs, static table, linear-scan `getOutput`" shape. The one real difference: CE's matching is **symmetric** (either input can fill either slot) and gated by a **momentum threshold**, not `CyclotronRecipes`' exact catalyst/target distinction — so use a `List<ParticleAcceleratorRecipe>` (not a `Map`, since the symmetric check needs to try both orderings per entry, matching CE's own `List` choice and its own `matchesRecipe` logic almost verbatim) rather than `CyclotronRecipes`' `Map<Pair<...>>`. This is the smallest and most mechanically simple of the three files (11 entries, no fluids, no duration/power fields at all — CE's Albion detector block presumably derives processing time from the physical particle-transit simulation, a separate concern from the recipe table itself).
- **Neither PlasmaForge nor ParticleAccelerator has a machine to attach the recipe data to yet** — see "Item/registry dependency check" above. Porting the recipe-data classes is still worthwhile groundwork (matches this project's own precedent — `CentrifugeRecipes`/`ChemPlantRecipes` etc. were all ported as data-only classes ahead of/alongside their block entities), but the implement wave should be told explicitly: **recipe data alone does not create reachability** until (a) the corresponding machine block/block-entity exists (Plasma Forge: none of CE's real `fusion_plasma_forge`/ICF-laser-fusion multiblock is built; Particle Accelerator: none of CE's real 7-class Albion multiblock — `PASource`/`PARFC`/`PADipole`/`PAQuadrupole`/`PABeamline`/`PADetector`/`TileEntityCooledBase` — is built), and (b) the blocked item families above (circuits, `item_expensive`, `part_generic`, the 8 `particle_*` items, the 3 new `Mats.java` materials) land.

## Open questions / risks

1. **CE's "expensive mode" (`GeneralConfig.enableExpensiveMode`, `inputItemsEx`) — port or drop?** 24 of PlasmaForgeRecipes' 35 entries carry an alternate, more expensive ingredient list gated by this global config toggle. This port has no equivalent global-difficulty-config precedent found elsewhere in the codebase during this research pass — recommend treating it the same way `ModRecipeProvider`'s javadoc already treats CE's ore-dict compatibility legs (documented, dropped, not replaced) unless a later phase specifically wants a difficulty-toggle system, but this is a judgment call for whoever implements it, not settled by this research.
2. **CE's "blueprint pool" (`setPools`/`setPools528`/`setPoolsAllow528`) and "auto-switch group" (`setGroup`) mechanics** — CE progression/UX layers (a research-unlock system and a GUI material-dropdown convenience) riding on top of the recipe data proper. Not investigated further in this pass (out of scope for a recipe-data catalog); the implement wave should treat these as metadata to note but not block on, unless CE's blueprint-unlock system turns out to be load-bearing for whether a recipe can be crafted at all (this report did not verify that either way).
3. **`machine_icf_press`/`machine_icf_controller` id collision risk flagged above** — worth a deliberate naming decision (rename this port's existing "ICF Reactor" family, or accept the id ambiguity) before PlasmaForgeRecipes' `icfcontroller`/`icfpress` outputs are wired to real blocks, so a future CE-faithful `icf_controller`/`machine_icf_press` (the laser-fusion multiblock's real controller/press) doesn't collide with or get confused for the already-built, differently-behaved blocks of the same/similar name.
4. **CE's `IFusionPowerReceiver` tokamak family (Boiler/Breeder/Collector/Coupler/Klystron/MHDT/PlasmaForge/Torus)** is a single, larger connected system this port's own `FusionBlocks.java` javadoc has already scoped out for a documented reason (missing `KlystronNetwork`/`PlasmaNetwork` network-provider abstractions, missing `ModuleMachineFusion` processing-loop base). Building the Plasma Forge machine block in isolation without that surrounding network system may not be meaningful — this is a scope/sequencing question for whoever plans the machine-building work, not resolved by this recipe-only research pass.
5. **Albion (Particle Accelerator) is a genuine multiblock physics simulation**, not a single machine block with a GUI (7 distinct tile-entity classes: source, RF cavity, dipole/quadrupole magnets, beamline, detector, a shared cooled-base). This is a substantially larger build than a typical single-block machine and was not scoped or estimated by this research task (out of a recipe-data-only assignment) — flagging so the implement wave doesn't underestimate it as "just add a block."

**In-CE structure**: this is **not** a table/loop-driven family — it is **12 individually-authored, individually-registered `IRecipe` objects** across 7 classes: 6 classes each contribute exactly one singleton instance (a fully dynamic, predicate-based `matches`/`getCraftingResult` pair, registered once with a fixed `ResourceLocation`), and the 7th class (`ContainerUpgradeCraftingHandler`) is a *reusable subclass* of Forge's `ShapedOreRecipe` instantiated 5 separate times with 5 different fixed shapes/ingredients/outputs (crate upgrades + mass-storage upgrades), each construction a literal one-off call inside `CraftingManager.java`'s ~1,200-line `addCrafting()` dispatcher — not looped over any table. So: **7 classes, 12 concrete recipe registrations total**, well under the "small file" threshold — every entry is catalogued below, not sampled.

Every one of the 6 non-`ContainerUpgradeCraftingHandler` classes overrides `IRecipe.matches`/`getCraftingResult` directly (CE 1.12.2's low-level recipe SPI) rather than declaring a static `ingredient -> output` shape — this is exactly the "dynamic, NBT/predicate-aware recipe with no fixed shape a plain JSON ingredient list cannot express" category this task's prompt names. `ContainerUpgradeCraftingHandler` is the one partial exception: it *does* have a fixed shaped-recipe shape (so its 5 instances *could* be JSON-authored for matching), but it overrides `getCraftingResult` to copy the source container's full NBT tag compound onto the output — a step no plain JSON shaped recipe can express either, so it still needs a custom `Recipe` class, just a narrower one.

## Already covered by this port

**The 7 handler classes themselves: 0% ported.** Confirmed by grep — no file anywhere under `src/main/java/com/hbm` implements `Recipe<CraftingInput>`, and this port's own already-committed code names all 7 explicitly as future work in two places:

- `src/main/java/com/hbm/datagen/ModRecipeProvider.java:82-86` (its own class javadoc, read directly): *"The 7 `com.hbm.crafting.handlers.*` CE classes (dynamic NBT/predicate-matching recipes: cargo shells, container upgrades, fluid duct retyping, grenades, MKU ammo, RBMK fuel assembly, scrap sorting) - these need genuine new `RecipeType`/`RecipeSerializer`/`Recipe<CraftingInput>` Java classes, not plain shaped/shapeless JSON, and are explicitly scoped by the research report as a separate, harder follow-up."*
- `docs/phase3/grenades.md:407-415` (Phase 3's own "Key design decisions", read in full) independently reaches the same conclusion for the grenade handler specifically, and is unusually precise about the target API: *"Vanilla's own `CustomRecipe`/`SimpleCraftingRecipeSerializer` shape (the mechanism behind vanilla's own match-predicate-plus-custom-result table recipes, e.g. tool repair/banner duplication) is the well-known NeoForge-era answer... but grepping this repo (including `upstream/neo-edition`) for `CustomRecipe`/`SimpleCraftingRecipeSerializer`/`RecipeSerializer` returns zero hits. Treat the exact class/method shape as unconfirmed until verified against the real 1.21.1 recipe API at implementation time."* This report reaches the identical recommendation independently (see "Recommended 1.21.1 implementation shape" below) and can now confirm the **item-side** half of that work is already done for grenades (see below) — only the recipe class itself remains open, exactly as that report left it.

**What genuinely IS already committed and directly reusable, per handler** (the real remaining gap is narrower than "nothing exists" for 4 of the 7):

1. **`ScrapsCraftingHandler` — the entire data model already exists, unused.** `src/main/java/com/hbm/items/machine/ItemScraps.java` (64 lines) already ports CE's scrap item exactly to this port's data-component convention: `ItemScraps.getAmount(stack)`/`create(scrapItem, amount, liquid)` read/write `MachineDataComponents.SCRAP_AMOUNT`/`SCRAP_LIQUID` (`src/main/java/com/hbm/items/machine/MachineDataComponents.java:134-140`). The only difference from CE is architectural, not missing: CE has one `scraps` `ItemEnumMulti` field (material = metadata, amount = NBT); this port has one `scraps_<material>` item **per** `NTMMaterial` (`MachineItems.java:512-518`, registered wherever `ItemScraps.isScrappable(material)`), with amount as the data component. This is *more* natural for the recipe than CE's shape, not less — see the catalog below.
2. **`RBMKFuelCraftingHandler` — the simulation AND the recycling-output math already exist, unwired.** `src/main/java/com/hbm/items/machine/ItemRBMKRod.java` (500 lines, fully ported) already exposes `getHullHeat`/`getCoreHeat`/`getEnrichment`/`getPoisonLevel` as static `ItemStack`-based accessors over data components — exactly CE's own gating conditions. `src/main/java/com/hbm/inventory/recipes/machine/rbmk/RBMKFuelRecipes.java` (67 lines) already ports the pellet-resolution (`getRecyclingOutput`, resolves rod→pellet by registry name via `RBMKRods.getPelletId`) **and** the exact enrichment/poison "stage" bucket math CE's handler inlines (`computeStage`, byte-for-byte the same `4 - clamp(ceil(enrichment*5-1),0,4)` + `+5 if poison>=0.5` formula as `RBMKFuelCraftingHandler.java:45-46`). **This class is currently called from nowhere in the codebase** (grepped: zero call sites in any block entity) — it exists purely as unwired scaffolding. **One real gap found in the existing code, not just a missing caller**: `getRecyclingOutput()` returns `new ItemStack(pellet, 8)` without ever calling `ItemRBMKPellet.setStage(...)` — the already-computed `computeStage()` result is never applied to the output stack it hands back. A new crafting-table recipe class wiring this up must call both methods and stitch them together (`ItemRBMKPellet.setStage(output, RBMKFuelRecipes.computeStage(rodStack))` before returning), not just call `getRecyclingOutput()` alone.
3. **`GrenadeCraftingHandler` — every ingredient item and the exact output-construction call already exist.** `src/main/java/com/hbm/items/weapon/grenade/GrenadeItems.java` (167 lines) registers all 4 CE component families 1:1 flattened (4 shells + 13 fillings + 5 fuzes + 4 extras = 26 items), and `ItemGrenadeUniversal.make(EnumGrenadeShell, EnumGrenadeFilling, EnumGrenadeFuze, EnumGrenadeExtra)` (`ItemGrenadeUniversal.java:184-188`) is the exact port-side equivalent of CE's `ItemGrenadeUniversal.make(shell, filling, fuze, extra)` the handler calls. `EnumGrenadeFilling.compatibleShells` (a `Set<EnumGrenadeShell>`, `EnumGrenadeFilling.java:59-67`) is also already ported and is the exact compatibility check CE's `matches()` needs. `GrenadeItems.java`'s own class javadoc (lines 36-44, quoted above) already documents this exact gap as the only missing piece.
4. **`CargoShellCraftingHandler`, `MKUCraftingHandler`, `FluidDuctRetypeHandler`: item-level dependencies are NOT ready** — see the dependency table below; these three are genuinely blocked on missing items/architecture, not just a missing recipe class.
5. **`ContainerUpgradeCraftingHandler`: 3 of its 5 concrete instances are fully item-ready** (crate_desh, crate_tungsten, safe); 2 are blocked (mass_storage tier, needs unregistered blocks/items) — see below.

**This port's own proven `Recipe<CraftingInput>`-adjacent precedent** (per this task's assignment, cross-referenced against Phase 5's machine-recipe classes): `src/main/java/com/hbm/inventory/recipes/AssemblerRecipe.java` (218 lines) and `src/main/java/com/hbm/inventory/recipes/machine/BreederRecipe.java` (127 lines), plus the smaller `HbmSimpleRecipe.java` (189 lines) they both build on, are the **only 3 classes in this codebase implementing `Recipe<T>` today** (grepped: `implements Recipe<` — 3 files, exactly these). All 3 are **machine-menu recipes** (`SingleRecipeInput`/a custom multi-slot `AssemblerRecipe.Input` record), never `Recipe<CraftingInput>` — no file anywhere in this port, and none in `upstream/neo-edition` either (grepped both, zero hits for `CraftingInput`, `CustomRecipe`, or any class `extends ShapedRecipe`/`extends ShapelessRecipe`), touches the actual crafting-table `Recipe<CraftingInput>` contract. **The general pattern transfers directly, though** — every structural piece an implementer needs is already proven-shape-correct here: a plain data-holding class implementing `Recipe<T>`'s 6-7 abstract methods, a nested nested `Serializer implements RecipeSerializer<X>` with a `MapCodec` (`RecordCodecBuilder.mapCodec`) for JSON and a `StreamCodec.composite` for network sync, registered via `DeferredRegister<RecipeType<?>>`/`DeferredRegister<RecipeSerializer<?>>` (the same convention `ProcessingRecipes`/`BreederRecipes` already use for `AssemblerRecipe`/`BreederRecipe`'s own `RecipeType`/`RecipeSerializer` holders — not read in this pass but referenced by both files above). Only the input-type swap (`SingleRecipeInput`/custom record → `CraftingInput`) and the `CraftingRecipe` interface's extra `category()` method are new territory; the codec/registration machinery is a direct copy of an already-working pattern.

## Full recipe/entry catalog (all 12 concrete registrations)

### 1. `CargoShellCraftingHandler` — embed any item as a 240mm artillery shell's payload

| Aspect | Detail |
|---|---|
| Grid shape | Any ≥9-cell grid (`canFit: width*height >= 9`) |
| Match | Exactly 2 non-empty stacks anywhere in the grid; neither may `hasContainerItem` (excludes bucket-style items); exactly one of the two must be `ModItems.ammo_arty` @ metadata 8, no NBT tag |
| Craft result | Copies the **matched `ammo_arty` stack itself** (count forced to 1), sets a `"cargo"` NBT compound on it equal to the *other* matched item's full serialized `ItemStack` (count forced to 1) |
| **CE quirk, preserved not silently fixed**: `getRecipeOutput()` (line 77, used only for static JEI/recipe-book display) declares `new ItemStack(ModItems.ammo_shell, 1, 8)` — a **different item family** than what `getCraftingResult()` actually returns (a re-tagged `ammo_arty`). This is either an inherited copy-paste artifact or an intentional "close enough for display" simplification in CE itself; port the *real* logic (`getCraftingResult`'s behavior), and either match `getRecipeOutput`'s CE value verbatim for display parity or flag the mismatch — don't silently "fix" it to be internally consistent, since that would deviate from CE's actual live behavior. | |
| Remaining slots | Untouched (all consumed to empty; no `getRemainingItems` special-casing) |

### 3. `FluidDuctRetypeHandler` — batch-retype N ducts to one fluid using a reusable identifier

| Aspect | Detail |
|---|---|
| Grid shape | Any ≥2-cell grid (`canFit: width*height >= 2`) |
| Match | Exactly one `ModItems.fluid_identifier_multi` stack; ≥1 stack of `ModItems.fluid_duct` or `Item.getItemFromBlock(ModBlocks.fluid_duct_neo)` (any metadata — CE uses `OreDictionary.WILDCARD_VALUE`); **any other item present fails the match entirely** (no foreign items tolerated) |
| Craft result | `new ItemStack(ModItems.fluid_duct, <total duct count in grid>, <identifier's primary fluid meta>)` — one batched output stack, all set to the identifier's currently-configured fluid type via `ItemFluidIDMulti.getType(idStack, true)` |

### 6. `RBMKFuelCraftingHandler` — recycle a cool, spent fuel rod into pellets

| Aspect | Detail |
|---|---|
| Grid shape | Any ≥1×1 grid (works in the player's personal 2×2 grid too, not just a crafting table) |
| Match | **Exactly one** non-empty stack anywhere in the grid; item `instanceof ItemRBMKRod` with non-null `pellet` field; `getHullHeat(stack) < 50 && getCoreHeat(stack) < 50` (must be cool — CE gates active/hot rods out) |

### 7. `ScrapsCraftingHandler` — split a scrap glob's material value in half

| Aspect | Detail |
|---|---|
| Grid shape | Any ≥1-cell grid |

| Craft result | 2× scraps of the **same material**, each carrying `amount / 2` (rounds down — CE accepts the rounding loss on odd amounts) |

## Recommended 1.21.1 implementation shape

**Six of the seven handlers (all but `ContainerUpgradeCraftingHandler`) map cleanly onto vanilla's `CustomRecipe`/`SimpleCraftingRecipeSerializer` pattern** — the mechanism vanilla itself uses for exactly this category of recipe (tool repair, banner duplication, firework star assembly, tipped arrows, map cloning/extending — "match an arbitrary predicate over the crafting grid, compute a result, no fixed JSON-declarable shape"). This is the same conclusion `docs/phase3/grenades.md` already reached independently for the grenade case; this report confirms it generalizes to the other 5 predicate-based handlers too (CargoShell, FluidDuctRetype, MKU, RBMKFuel, Scraps all share the identical "scan all N slots, no positional shape, custom match+assemble" structure). Concretely, per handler:

- `class XRecipe implements Recipe<CraftingInput>` (not `CraftingRecipe` directly needed as an interface name, but implement its contract: add `CraftingBookCategory category()` alongside the usual `matches`/`assemble`/`canCraftInDimensions`/`getResultItem`/`getSerializer`/`getType` — the same 6-method shape `AssemblerRecipe`/`BreederRecipe` already implement for `Recipe<T>`, plus this one extra method for the crafting-table variant). `CraftingInput` (this port's `AssemblerRecipe.Input` custom record is the closest already-committed precedent for "a plain multi-slot input snapshot") exposes `size()`/`getItem(int)` directly — since none of these 6 handlers' `matches()` logic actually depends on grid width/height/row/col (they all scan "every non-empty slot" without positional meaning; CE's `getStackInRowAndColumn(i%3, i/3)` loops are enumeration-order artifacts of CE's grid API, not real positional requirements — confirmed by re-reading each `matches()` body), a straight `for (i=0; i<input.size(); i++) input.getItem(i)` loop is a faithful, *simpler* translation, not a simplification with behavior risk.
- Register each recipe's `Serializer` as a `SimpleCraftingRecipeSerializer<X>`-style wrapper (vanilla's own class for exactly "no JSON-configurable fields beyond `category`") — or, following this port's own `HbmSimpleRecipe.Serializer`/`AssemblerRecipe.Serializer` convention more literally, a hand-written `RecipeSerializer<X>` with a trivial `MapCodec` (since these recipes carry no per-instance configurable data at all — every "input" is hardcoded Java logic, not JSON-declared ingredients) and a no-op `StreamCodec`.
- **Still author one minimal JSON stub per recipe** under `data/hbm/recipe/<id>.json` (e.g. `{"type": "hbm:cargo_shell_crafting"}`), generated via datagen (`RecipeProvider`'s special-recipe helper) — this is the idiomatic modern-NeoForge translation of CE's `hack.getRegistry().register(new X().setRegistryName(...))` direct-instance registration: keeps the recipe inside `RecipeManager`'s normal datapack-reload lifecycle (works with `/reload`, JEI/REI recipe-book integration point) while all real logic still lives in Java, matching CE's own "one Java-authored recipe object, trivially identified" intent.
- **Grouping by exact fit today**:
  - **`GrenadeCraftingHandler` → ready to build now.** Every item dependency exists; only the recipe class is new work. Recommend building this one first as the template the other predicate-based handlers copy.
  - **`RBMKFuelCraftingHandler` → ready to build now**, and should **also fix the `setStage` wiring gap** found in this pass (`RBMKFuelRecipes.getRecyclingOutput` never calls `ItemRBMKPellet.setStage`) as part of landing the recipe, not as a separate follow-up — the recipe class is the natural place to stitch `getRecyclingOutput()` + `computeStage()` + `setStage()` together.
  - **`ScrapsCraftingHandler` → ready to build now.** All supporting logic exists; note the match condition should key off `stack.getItem() instanceof ItemScraps` (this port has one item id per material, unlike CE's single multi-material item) rather than a single fixed `ModItems.scraps` reference, and the "same material" constraint CE enforces implicitly (only one non-empty stack is ever allowed at all, so "same material" is automatically satisfied) carries over unchanged.
  - **`CargoShellCraftingHandler`, `MKUCraftingHandler` → defer.** The recipe-class work itself is no harder than Grenade/RBMKFuel/Scraps, but building it now would register a recipe with `matches()`/`getCraftingResult()` referencing item ids that don't exist yet, which either won't compile or requires stubbing several new items purely to unblock a recipe class — recommend landing these only once `ammo_arty`/`ammo_shell` (CargoShell) or `dust`/`morning_glory`/`syringe_metal_empty`/`syringe_mkunicorn` (MKU) land from whichever item-registration pass owns them (MKU's items in particular look like straightforward `ItemBase`/consumable registrations, not blocked on anything structural — likely a quick unblock whenever that pass happens).
  - **`FluidDuctRetypeHandler` → do not port literally; re-scope or skip.** See Open Questions.

**`ContainerUpgradeCraftingHandler` needs a different, narrower shape**: since it *does* have a fixed, JSON-declarable shape (unlike the other 6), the right translation is a class that **composes** a `ShapedRecipePattern` (vanilla's own JSON-shape codec, in use since 1.20 for `ShapedRecipe` itself) for `matches`/`getIngredients`/`canCraftInDimensions`, but overrides `assemble()` to run the normal shaped-result construction and then copy the found "container" ingredient's full `DataComponentPatch` onto the result (`stack.applyComponents(...)`/equivalent) — the 1.21.1 data-component analog of CE's `NBTTagCompound` copy. This is genuinely a hybrid: JSON-authorable shape (5 files under `data/hbm/recipe/`, one per tier, letting datagen produce them the same way `ModRecipeProvider` already produces its other shaped recipes) + one small custom `RecipeSerializer` (decodes `ShapedRecipePattern.CODEC` + a `result` field, same as vanilla's own `ShapedRecipe.Serializer`, wrapping the component-copy `assemble()` override) — not a from-scratch predicate recipe like the other 6. Recommend landing only the 3 item-ready tiers (crate_desh/crate_tungsten/safe) first; the 2 mass-storage tiers need the `circuit`/`mass_storage_*` item work first regardless of recipe-class readiness.

**Caveat carried over from this port's own established practice** (matching `HbmSimpleRecipe.java`'s own javadoc caveat, `AssemblerRecipe.java`'s, and `docs/phase3/grenades.md`'s): the exact `CustomRecipe`/`SimpleCraftingRecipeSerializer`/`CraftingInput` method signatures above are stated from well-established, stable 1.20.5+ vanilla recipe-codec API knowledge, **not confirmed by compiling against the real NeoForge 21.1.228 jar** — this sandbox has no network access to Maven (the same constraint every other phase's research has already disclosed) and no cached NeoForge/Minecraft jar or decompiled source is available locally to double-check field/method names before implementation. Whoever lands this should verify against the real jar before relying on exact signatures, exactly as `HbmSimpleRecipe.java`'s own javadoc already asks of its readers for the machine-recipe case.

## Open questions / risks

1. **`FluidDuctRetypeHandler` is the one handler where "port it" may be the wrong instruction entirely.** CE's item model (a typed duct *item* you retype before placing) and this port's model (an untyped duct *block* you retype in-world by right-clicking with an identifier tool) solve the same player-facing problem through architecturally different means, and this port's `ItemFluidIDMulti`/`ItemFFFluidDuct` already cover the functional intent (batch pre-typing, in-place retyping, flood-fill retyping a network) without needing a crafting-table recipe at all. Porting the CE recipe literally would require inventing a "typed duct item" concept this port has deliberately avoided (per `ItemFFFluidDuct`'s own class javadoc, cited above) purely to give this one recipe something to consume/produce. Recommend flagging this to whoever scopes the actual implementation wave as a candidate to **skip or explicitly re-scope** (e.g., "no crafting recipe needed here, already covered by X/Y") rather than building it as literally specified — but this report does not have the authority to make that scope call unilaterally, so it's raised here rather than silently dropped.
2. **CE's `CargoShellCraftingHandler.getRecipeOutput()` inconsistency** (declares `ammo_shell` while the real logic produces a retagged `ammo_arty`) should be resolved deliberately when this handler is eventually built — follow the real `getCraftingResult()` behavior (this is almost certainly what actually happens in live CE gameplay, since `getRecipeOutput()` in 1.12.2's `IRecipe` contract is JEI/recipe-book display only, never consulted by the actual crafting grid), but the display-only mismatch means a straight 1:1 "port both methods as written" would produce a recipe whose JEI preview doesn't match its real output — worth a one-line decision (preview the real output type, or preview CE's stated type for exact display parity) rather than an unexamined copy.
3. **MKU's `Level.getSeed()` per-world-random shape has no precedent anywhere in this port's already-committed recipe code** (`AssemblerRecipe`/`BreederRecipe`/`HbmSimpleRecipe` are all static-shape-once-loaded). This isn't a blocker (the `matches(CraftingInput, Level)` signature already receives a `Level`, exactly what's needed to call `level.getSeed()`), but it is the one handler among the 6 predicate-based ones that reads mutable per-world state inside `matches()` rather than pure item/stack state — worth a second look at implementation time to confirm caching (`lastSeed`/`MKURecipe` static fields in CE) is still safe under NeoForge's recipe-manager reload lifecycle (a `RecipeManager` reload happens on `/reload` and datapack changes; CE's static-field cache was written for a single-JVM-per-world 1.12.2 client/server, and this port should confirm the cache correctly resets or stays valid across a world change / reload rather than leaking a previous world's seed-derived pattern).
4. **This report did not verify the exact call-site context CE wraps the 5 `ContainerUpgradeCraftingHandler` instantiations in** (`CraftingManager.java` lines 1166-1187 were read as complete one-line statements, but the enclosing method call — likely `GameRegistry.addRecipe(...)` or a local helper — was not traced) — low-risk (the 5 statements themselves are complete and were read in full with all pattern/key data), but noted for completeness since this report's own instructions ask for exactness.
5. **The exact data-component this port's crate/mass-storage block entities already use (if any) to preserve contents across a block break→item→re-place cycle was not confirmed** — `BlockStorageCrate.java`/`CrateBlockEntity.java` were spot-checked but the precise component name (`DataComponents.BLOCK_ENTITY_DATA`/a custom one) an implementer should copy in `ContainerUpgradeCraftingHandler`'s port was not pinned down in this pass; flagged rather than guessed.
6. **CE's exact meaning of `ammo_arty` metadata 8** ("smoke"? a specific shell type?) was not independently verified against CE's `ModItems.java`/`ItemAmmoArty` in this pass — not needed to catalog the recipe's *mechanism*, but relevant once CargoShell's blocking item-registration work actually happens (whoever ports `ammo_arty` should confirm which of its variants is meta 8 before wiring this recipe to it).

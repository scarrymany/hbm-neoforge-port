## Scope confirmed

**CE `MatDistribution.java` is Java-table-backed, not JSON-backed**, despite the class's `getFileName()`/`readRecipe`/`writeRecipe` machinery suggesting otherwise. It extends `SerializableRecipe` (CE `.../recipes/loader/SerializableRecipe.java`), whose `initialize()` (lines 98-147, read in full) does, per recipe-handler class: delete existing entries, then **either** read an admin-dropped override file from `config/hbmRecipes/<getFileName()>` (`hbmCrucibleSmelting.json`) if one exists on disk, **or**, if no such file exists (the shipped-mod default state), call `registerDefaults()` — the Java method. `registerDefaults()` (`MatDistribution.java` lines 74-136) is therefore the canonical, ship-in-the-jar data; the JSON path is a live-server-admin customization/persistence feature layered on top, structurally identical to the pattern this port has already declined to carry forward elsewhere (`HazmatRegistry`'s own javadoc, cited in `CommonEvents.java` line ~67: "this port splits out just the `initDefault()` half... Gson config-file persistence is not ported").

**Structure: a flat sequence of static-method calls inside one `registerDefaults()` override, no loop except one.** 15 `registerOre(String key, Object... matDef)` call sites (one of which, `TH232`, wraps a 6-iteration `for` loop over `OreDictManager.TH232.all(MaterialShapes.ORE)` — CE's ore-dict alias-spelling mechanism, explained below) and 27 `registerEntry(Object key, Object... matDef)` call sites (one, `Items.MINECART`, is a byte-for-byte duplicate of an earlier call — dead/overwritten data, not a second logical entry). **42 source call-site lines total, 41 logically distinct entries** — well inside the "small file, catalog everything" threshold. Two static helper methods (`registerEntry`/`registerOre`, lines 37-71) do the actual `List<MaterialStack>` construction and `Map` insertion; `registerDefaults()` is pure data.

Both `registerEntry`/`registerOre` are declared **directly on `MatDistribution` itself in CE** (not on `Mats`) and write into `Mats.materialEntries`/`Mats.materialOreEntries` via `import static com.hbm.inventory.material.Mats.*`. **This port's seam methods with the identical names already live on `Mats` itself** (see next section) — a structural simplification (one fewer class/indirection layer) this port already made, not something a MatDistribution port needs to re-introduce.

## Already covered by this port

**The seam is already built and its calling convention is confirmed exactly.** `src/main/java/com/hbm/inventory/material/Mats.java`:

- Line 229: `public static void registerEntry(Item key, Object... matDef)` — builds a `List<MaterialStack>` from `matDef` (alternating `NTMMaterial, int` pairs, validated even-length) and puts it into `materialEntries` (a `Map<Item, List<MaterialStack>>`, line 49).
- Line 236: `public static void registerOre(String key, Object... matDef)` — same `matDef` parsing, puts into `materialOreEntries` (a `Map<String, List<MaterialStack>>`, line 51), **keyed by tag path** (confirmed by the method's own javadoc, line 235: "registers the materials an ore-dict/tag name yields") and by `getMaterialsFromItem`'s actual lookup (line 256): `stack.getTags().map(tag -> materialOreEntries.get(tag.location().getPath()))`.
- `toMaterialStacks(Object...)` (private, line 242) is the shared `matDef`-parsing helper both public methods call — behaviorally identical to CE's inlined per-method loop.

**Divergence from CE's signature, both deliberate simplifications already made by this port, not gaps to fix:**
1. CE's `registerEntry(Object key, ...)` accepts `Item`/`Block`/`ItemStack`/`ComparableStack` and normalizes to a `ComparableStack` (CE `MatDistribution.java` lines 37-46). The port's version takes `Item` only. **Practical effect:** every CE call site passing a `Block` constant (`Blocks.OBSIDIAN`, `Blocks.RAIL`, `Blocks.GOLDEN_RAIL`, `Blocks.DETECTOR_RAIL` — 4 of the 41 entries) needs `.asItem()` appended when transcribed. Every CE call site passing a metadata-carrying `ItemStack` (`DictFrame.fromOne(item, enumOrdinal)`, or `new ItemStack(Items.COAL, 1, 1)`) has **no literal translation at all** — it must instead target whichever single flattened `Item` id this port's DataComponents-based model gave that CE metadata variant (see per-entry table below). This is strictly simpler than CE's own mechanism, not harder.
2. CE's key-matching for the ore/tag map is a **live ore-dict-name string match** (`ItemStackUtil.getOreDictNames(stack)`, computed at lookup time from Forge's `OreDictionary`). This port's key-matching is a **live NeoForge item-tag match** (`stack.getTags()`, computed from whatever `ItemTagsProvider`-generated tag JSON actually applies to that item at runtime) — the direct, idiomatic 1.21 replacement for Forge ore-dict, already fully wired.
3. `Mats.getMaterialsFromItem` (port, lines 252-280) and `Mats.getSmeltingMaterialsFromItem` (port, lines 282-287) are **already a faithful behavioral port of CE's identically-named methods** (CE `Mats.java` lines 190-239, read in full and diffed). One confirmed minor divergence: CE's single `for` loop over ore-dict names does one combined `break outer` the instant *either* an exact-`materialOreEntries` key *or* a generic prefix-tier match succeeds, so at most one ore-derived material list is ever added, and it stops scanning further ore-dict names entirely. The port instead runs the exact-tag lookup and the generic-tag (`tagToMaterial`) lookup as two **independent** `findFirst()` streams, so a real item carrying tags that satisfy both could contribute both, where CE would have contributed only one. Low practical risk (no port-side item is known to carry both an exact `materialOreEntries`-matched tag and an autogen-shape tag simultaneously today) — flagged in Open Questions.
4. `Mats.specialCaseResolvers` (port, line 193, a `List<Function<ItemStack, MaterialStack>>`) is **already the confirmed seam** for CE's one hardcoded special case inside `getMaterialsFromItem` (CE `Mats.java` line 227: `if (stack.getItem() == ModItems.scraps) list.add(ItemScraps.getMats(stack));`) — the port's own javadoc names this exact CE mechanism as the resolver's motivating example. `ModItems.scraps`/`ItemScraps` are not registered in this port yet (grep: `items/machine/ItemScraps.java` exists as a class but its scrap-item family is part of `MachineItems.java`'s 82-material `scraps_` predicate — per `docs/phase6/recipe_graph_audit.md` §4's `MachineItems.java` row, cited there as "82-material `scraps_` predicate" already registered) — wiring the resolver is a follow-up for whichever area owns `ItemScraps.getMats`, not part of this seam itself.

**What is NOT yet done, i.e. the real remaining gap this phase must close:** `materialEntries`/`materialOreEntries` are **populated by zero call sites anywhere in this port** — confirmed by `grep -rn "Mats.registerEntry\|Mats.registerOre" src/main/java/com/hbm` returning nothing outside `Mats.java`'s own method declarations. The seam exists and is correctly shaped; no caller has ever invoked it. This phase's job is exactly that caller.

**A second, equally load-bearing gap this research uncovered (not previously documented anywhere in `docs/phase6/`): the generic ore-dict-name auto-smelting tier CE relies on for the *overwhelming majority* of its smeltable items is only half-wired on the port side.** Full explanation in the next section — this matters as much as porting `MatDistribution.java` itself.

### The two-tier lookup CE actually uses (and what each tier needs from this port)

CE's `Mats.getMaterialsFromItem` (CE `Mats.java` lines 190-232, read in full) is **not** solely driven by `MatDistribution.java`. It has two tiers:

- **Tier 0 (curated, exact match):** `materialOreEntries.get(oreDictName)` / `materialEntries.get(exactItem)` — a direct hit on something `MatDistribution.registerDefaults()` explicitly registered. This is the ~41-entry file this research catalogs below.
- **Tier 1 (generic, automatic, NOT part of `MatDistribution.java` at all):** if no Tier-0 hit, CE walks every ore-dict name the stack carries against every registered `MaterialShapes` prefix (`MaterialShapes.prefixByName`, e.g. `"ingot"`, `"nugget"`, `"dust"`...). If a name starts with a known prefix and the remainder resolves via `Mats.matByName` to a smeltable/additive `NTMMaterial`, it auto-adds `MaterialStack(material, prefixShape.q(1))` — i.e. **any item CE registered under the ore-dict name `<shapeprefix><MaterialName>` (e.g. `"ingotTitanium"`) auto-smelts back into exactly 1 unit of that shape's own material, with zero explicit registration needed.** This is precisely how CE's ~350 hand-named `ingot_`/`nugget_`/`billet_`/`powder_`/`plate_`/`crystal_` items (this port's `IngotNuggetItems`/`BilletPowderItems`/`PlateCrystalWasteItems`) become crucible-smeltable in CE at all — `MatDistribution.java` never mentions them individually.

**This port already re-implemented Tier 1 as a precomputed map** (`Mats.tagToMaterial`, built once in the `static {}` block at lines 195-204, keyed by `shape.commonTag(mat)` for every `orderedList` material × every autogen shape with a non-null `tagFolder`) — this is the exact architectural analogue of CE's live prefix-strip loop, confirmed correct. **But it only fires for items that actually carry the corresponding `c:<tagFolder>/<material>` tag at runtime**, and this port's tag datagen (`src/main/java/com/hbm/items/datagen/ModItemTagProvider.java`, read in full) **only tags items registered under `MaterialShapes.buildRegistryName(mat)`'s naming convention** (`<material>_<shape>`, e.g. `titanium_ingot`) — its own javadoc says so explicitly (lines 28-32): *"CE-legacy hand-ported items that keep CE's original prefixed ids (e.g. `ingot_steel`) live in a different naming scheme and are intentionally not matched here."* That naming convention is exactly `MaterialItemGenerator`'s (17 shapes) and `MaterialBlockGenerator`'s (BLOCK shape) — **it is not `IngotNuggetItems`/`BilletPowderItems`/`PlateCrystalWasteItems`'s naming convention** (`ingot_titanium`, `powder_iron`, `plate_gold`, prefix-first, CE-legacy).

**Net effect, stated precisely:** once a Crucible mechanism exists and `MatDistribution.java`'s 41 curated entries are ported, Tier-1 auto-smelting will work for free for `MaterialItemGenerator`'s ~188 items and `MaterialBlockGenerator`'s 57 blocks (already tagged) — but **will silently do nothing for `IngotNuggetItems` (184) + `BilletPowderItems` (176) + `PlateCrystalWasteItems` (107) = 467 items**, because none of them carry the tag `Mats.getMaterialsFromItem` looks for, even though CE's real behavior smelts every one of their CE counterparts back into 1 unit of its own material via exactly this mechanism. **This is the single most important, previously-undocumented finding of this research task** and belongs in Phase 7's implementation plan as its own line item, not folded silently into "port `MatDistribution.java`."

## Item/registry dependency check — summary

**Ready to port now (28 of 41 entries, ~68%):** all 2 vanilla-block-tag entries (stone/cobblestone), all 4 vanilla-`Block` entries (obsidian/rail/golden_rail/detector_rail), the minecart entry, both `blades_*` castables, all 5 `stamp_*_flat` castables, all 13 "actual ore" `registerOre` entries (iron/titanium/tungsten/aluminium/coal/gold/uranium(partial)/thorium/copper/lead/beryllium/cobalt/redstone), both hematite/malachite ore entries, the limestone/flux/charcoal entries. Every target item this list needs already exists in the port's registry today (spot-checked by grep per row above, not assumed).

**Blocked (13 of 41 entries, ~32%), grouped by missing item family:**
- `blade_titanium`/`blade_tungsten` (2 entries) — explicitly out-of-scope per `MachineItems.java`'s own comment, not a bug to fix incidentally; needs that area's owner to register them first.
- `pipes_steel` (1 entry) — CE's hand-coded plumbing item, distinct from the generic autogen `steel_pipe`; needs a new registration, not a rename.
- `casing` / `EnumCasingType` (4 entries: SMALL/SMALL_STEEL/LARGE/LARGE_STEEL) — enum shell exists, item family does not.
- `chunk_ore` / `EnumChunkType.CRYOLITE` (1 entry) — enum shell exists, item family does not.
- `powder_ash` / `EnumAshType` (3 entries: WOOD/COAL/MISC) — enum shell exists, item deliberately excluded pending a flattening-naming decision (`BilletPowderItems.java`'s own javadoc).

None of these 13 blocked entries needs new recipe *logic* — every one is blocked purely on a missing `Item`/`Block` registration in a different, already-identified area (weapon/machine casing family, chunk-ore family, ash-powder family). **Recommendation: port all 28 ready entries now; leave the 13 blocked ones as commented-out TODOs citing the exact missing item, matching this port's own established convention** (e.g. `IngotNuggetItems.java`'s own `// TODO(...)` style) so nothing is silently dropped and the eventual item-registration areas have an exact pointer back to reconnect.

## Recommended 1.21.1 implementation shape

**Plain Java class, invoked once from `FMLCommonSetupEvent`'s `enqueueWork` — not a JSON datapack, not a new `RecipeType`/`RecipeSerializer`.** Rationale:

1. **Faithful to what CE itself treats as canonical.** As established in Scope Confirmed, CE's own `SerializableRecipe.initialize()` only reads a JSON file when a server admin has explicitly dropped one in `config/hbmRecipes/` — the shipped-mod behavior is 100% `registerDefaults()` Java code. Porting the JSON-round-trip/live-reload half (`readRecipe`/`writeRecipe`/file-watching) would port a rarely-used admin-customization feature this project has already declined to carry forward for the structurally identical `HazmatRegistry` case (cited above).
2. **Matches this port's own established precedent for exactly this class of CE recipe data.** `docs/phase6/recipe_graph_audit.md` §3.4 documents that `CrystallizerRecipes`/`MixerRecipes`/`RefineryRecipes`/`CentrifugeRecipes`/etc. are *already* ported as "real, ported CE recipe data as plain Java... a deliberate, documented design choice" specifically because their shape (competing entries, multi-key structure) "doesn't fit vanilla's `Recipe<RecipeInput>` contract." `MatDistribution` is the same shape: a `Map<Item/String, List<MaterialStack>>` with no crafting-grid/inventory matching semantics at all — there is no sensible vanilla `RecipeType` to bend it into.
3. **Concrete hook point, already established and precedent-backed.** `src/main/java/com/hbm/main/CommonEvents.java` line 54's `commonSetup(FMLCommonSetupEvent event)` already runs `RefineryRecipes.registerRefinery()`, `CentrifugeRecipes.register()`, `GasCentrifugeRecipes.register()`, `SILEXRecipes.register()` inside its `event.enqueueWork(...)` block, with an in-line comment explaining exactly why this timing is required ("resolves `DeferredItem.get()` eagerly while building its `ItemStack` outputs... calling them from a block `registerAll()`... threw `IllegalStateException` at startup"). A `MatDistributionDefaults.registerAll()`-style method (calling `Mats.registerEntry`/`Mats.registerOre` ~28+ times per the ready-entries table above) belongs in this exact same `enqueueWork` block, for the identical reason: it needs `BuiltInRegistries.ITEM` fully populated (true once `RegisterEvent` has fired, i.e. by the time `enqueueWork`'s `Runnable` executes) to resolve item references like `MachineItems.BLADES_STEEL.get()` or a vanilla `Blocks.RAIL.asItem()`.
4. **For the 13 "actual ore" `registerOre` entries specifically, recommend `registerEntry` (exact-item) over `registerOre` (tag-path) at the implement-wave's discretion**, since `OreBlocks.java` currently exposes no public per-ore accessor and no common family tag for its ~68 ore blocks (confirmed: only `registerAll()` is public, `ore()`/`cluster()`/`depthOre()` are private and don't return named fields except `blockMeteor`). Two paths, either acceptable: (a) add a small `Map<String, DeferredBlock<?>>` accessor to `OreBlocks.java` (outside this file's own scope, a one-line addition elsewhere) and call `Mats.registerEntry(OreBlocks.get("ore_titanium").get().asItem(), ...)`; or (b) resolve items by string id via `BuiltInRegistries.ITEM.get(ResourceLocation.fromNamespaceAndPath("hbm", "ore_titanium"))` at `enqueueWork` time — the same pattern `ModItemTagProvider.addTags()` already uses (`BuiltInRegistries.ITEM.getOptional(id)`), needing zero edits to `OreBlocks.java`. Path (b) is the lower-friction choice for a self-contained MatDistribution port.
5. **Close the Tier-1 tag gap as part of the same implementation pass, not as a separate follow-up.** Since `ModItemTagProvider.addTags()` (lines 58-71) is already a clean, self-contained loop over `Mats.orderedList x MaterialShapes.allShapes` matched by `buildRegistryName`, the mechanical fix is a second loop in the same method (or a sibling private method) that instead resolves each `IngotNuggetItems`/`BilletPowderItems`/`PlateCrystalWasteItems` hand-named field's registry id by the CE-legacy `<shapeprefix>_<material>` naming pattern (e.g. try `"ingot_" + mat.getRegistryName()`, `"nugget_" + mat.getRegistryName()`, `"billet_" + mat.getRegistryName()`, `"powder_" + mat.getRegistryName()`, `"plate_" + mat.getRegistryName()`, `"crystal_" + mat.getRegistryName()` against `BuiltInRegistries.ITEM`) and tags any hit into the same `shape.commonTag(mat)`. This single change is what actually connects the curated `MatDistribution.java` port's ore entries through to the ~467 legacy-named items that make up most of `MaterialItemGenerator`/`IngotNuggetItems`/`BilletPowderItems`/`PlateCrystalWasteItems`'s reachability — without it, this phase's headline "unblocks 700+ items" claim only delivers on the `MaterialItemGenerator`+`MaterialBlockGenerator` fraction (~245 items) plus whatever the Crucible block/GUI itself later exposes.

**None of this requires the Crucible block/block-entity/GUI/multiblock itself to exist yet** — `Mats.registerEntry`/`registerOre` and the tag-provider fix are pure data/registry wiring, independently testable via `Mats.getSmeltingMaterialsFromItem(stack)` unit-style checks before any Crucible UI exists. The Crucible mechanism itself (CE: `TileEntityCrucible.java`, `MachineCrucible.java`, `GUICrucible.java`, `ContainerCrucible.java`, `CrucibleRecipes.java` for the melt-duration/heat-cost side, `RenderCrucible.java`/particles) is a separate, larger implementation task this research did not scope (out of this assignment's remit — CE's `TileEntityCrucible.java` was not read).

## Open questions / risks

1. **Scope correction to `docs/phase6/recipe_graph_audit.md`'s framing.** That report's §2 cause 1 attributes "over 700 items" directly to "CE's Crucible/`MatDistribution` smelting-and-casting system... not ported at all," which is accurate about the *mechanism's absence* but could be read as implying `MatDistribution.java` alone (once ported) unblocks all 700+. This research's material-level mapping shows `MatDistribution.java`'s 41 entries only ever produce ~19 distinct materials (stone/obsidian/iron/gold/redstone/titanium/tungsten/steel/aluminium/sodium/weaponsteel/gunmetal/carbon/copper/lead/thorium/uranium/beryllium/cobalt/hematite/malachite/flux — 22 counting blocked ones), out of ~90 total `NTMMaterial` constants. The remaining ~68 materials' items (essentially everything transuranic, every advanced alloy, every plastic) need entirely different CE recipe classes (breeder, nuclear transmutation, blast furnace, and the ~60 other un-ported machine-recipe classes) that are out of this specific file's scope. **Recommend the Phase 7 plan explicitly track "MatDistribution port" and "Crucible mechanism + full material coverage" as two separate, sequenced deliverables**, not one, to avoid the 700+ figure being silently treated as fully closed once this one file lands.
2. **The uranium-ore 7th alias (`ore_sellafield_uranium_scorched`) not existing anywhere in this port** is consistent with `recipe_graph_audit.md`'s finding that structure/POI world-gen is entirely unbuilt (Sellafield reads as a named-location/structure variant in CE) — low-risk, single-item gap, not investigated further here since structure world-gen is explicitly a different phase's scope (Phase 8 per this project's own task list).
3. **The `getMaterialsFromItem` Tier-0/Tier-1 `findFirst()`-vs-`break outer` divergence** (Already Covered §, point 3) is a genuine, if narrow, behavioral difference from CE. No concrete port-side item is known today to trigger it (would need an item carrying both an exact-tag-registered ore alias *and* a generic autogen material tag simultaneously), but it's worth a one-line unit-test-style check once the Crucible consumes this data for real, rather than assuming CE-identical output blindly.
4. **`Mats.specialCaseResolvers` is unpopulated** — CE's one live use (`ModItems.scraps` -> `ItemScraps.getMats(stack)`, a randomized-material scrap-recycling mechanic) maps to this port's `MachineItems.java` 82-material `scraps_` predicate family per `recipe_graph_audit.md` §4, but this research did not trace `ItemScraps.java`'s current implementation state closely enough to say whether `getMats`-equivalent logic already exists there or still needs writing — flagged for whoever picks up the resolver wiring, not resolved here.
5. **CE's `DictFrame.fromOne`/metadata-`ItemStack` entries (the 4 casing + 1 chunk_ore + 3 powder_ash = 8 blocked entries) all depend on other areas' item-family decisions**, specifically how each CE `ItemEnumMulti`-backed field gets flattened into 1.21 ids (the exact naming convention isn't fixed yet per `BilletPowderItems.java`'s own javadoc for `powder_ash`). This research intentionally does not guess those names to avoid the port committing to an id another area might choose differently — the blocked-entry table above names the CE ordinal/material precisely enough (e.g. "MAT_ALUMINIUM, INGOT.q(1), MAT_SODIUM, INGOT.q(1)" for cryolite) that reconnecting them is a one-line change whenever those items land.
